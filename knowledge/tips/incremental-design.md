# Incremental Design Tips

## 目的

最小差分の積み重ねで設計が腐らないよう、再設計を「機会的」ではなく「計画的」に行う。

## 大前提

- 最小差分ルールは維持する。task のついでに構造を変える機会的リファクタリングは引き続き禁止。
- 再設計は専用の task / Story として行い、通常の実装 task と混ぜない。
- 「必要なタイミング」は感覚ではなく、次の 2 つのトリガーで判定する。

## トリガー 1: 変更駆動（準備リファクタリング）

原則は「まず変更を簡単にし、それから簡単になった変更をする」（Make the change easy, then make the easy change）。再設計の最適タイミングは、次の変更が現行構造と喧嘩する瞬間である。

worker が FileChangePlan を書く時点で判定する。歪んだ差分の兆候:

- 既存関数への不自然な分岐追加でしか要件を満たせない
- 責務の合わない場所にロジックを押し込むことになる
- 同じ修正を複数箇所へコピーすることになる
- 「既存に合わせたが、なぜこうなるか説明できない」構造になる

該当したら、そのまま実装に進まない。manager へ次の分割を提案する。

1. 振る舞いを変えない準備リファクタリングの task
2. 簡単になった構造の上で本来の変更を行う task

準備リファクタリング task の条件:

- 既存テストをグリーンに保ったまま行う
- 挙動変更を一切含めない
- 本来の変更と同一 task に混ぜない

## トリガー 2: 負債駆動（歪みの台帳）

一回一回は正しい最小差分でも、蓄積すると構造が腐る。軋みシグナルの例:

- 同一ファイルが直近の task で繰り返し変更されている
- 同種の重複が 3 回目に達した
- ファイルの行数が肥大し続けている
- reject が同じ領域に集中している
- 「既存に合わせたが不自然」という task comment が反復している

worker / reviewer はこれらに気づいたら、**自分で直さず**、title の先頭に `[design-strain]` を付けた単発 task（storyId なし）として `issue_task` で記録する。記録には次を含める。

- 対象ファイル・領域
- 観測した事実（回数、行数、reject 履歴など）
- 気づいた元の task への参照

シグナルの評価と再設計の判断は manager が `design-review` skill で行う。worker / reviewer は記録までが責務である。

## 再設計 task の安全条件

- 現行挙動を固定する characterization テストを先に書き、グリーンを確認してから構造を変える
- 振る舞い変更と構造変更を同一 task に混ぜない
- スコープ（触る範囲・触らない範囲・壊してはいけない挙動）を manager が Story / task に明示する

## 再設計「しない」条件

次に当てはまる場合、シグナルがあっても再設計しない。

- 理由が美しさだけで、変更が困難になっている具体的な証拠がない
- その領域に次の変更予定がない
- シグナルが 1 件だけで、反復の証拠がない
- 安定していて誰も触っていない領域である

## Anti Patterns

- task のついでに「気づいたので」構造を変える（機会的リファクタリング）
- 構造と喧嘩していると気づきながら、歪んだ最小差分を黙って積む
- 振る舞い変更とリファクタリングを 1 つの task で行い、レビュー不能にする
- characterization テストなしで大きな構造変更を行う

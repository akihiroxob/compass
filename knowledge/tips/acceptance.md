# Acceptance Tips

## 目的

manager の最終受入を、Task の完了確認だけでなく、要求とシステム全体の整合性を保証する判断として行う。

## Reviewer と Manager の違い

- reviewer は、実装が Task の完了条件、既存構成、設計原則、検証基準を満たすか確認する。
- manager は、成果が人と合意した要求と親 Story の目的を満たし、Project 全体へ取り込んでよいか最終判断する。

Reviewer の承認は重要な証拠だが、Manager の判断を代替しない。

## 受入で照合するもの

次を相互に照合する。

1. 人と確認した要求・制約
2. 親 Story の目的・完了条件
3. Task の完了条件
4. Project の `AGENTS.md` と主要設計資料
5. worker / reviewer のコメントと検証結果
6. 実際の差分、成果物、外部から観測できる振る舞い

資料間で矛盾し正しい期待を決められない場合は、推測で Accept しない。矛盾点と必要な判断を明示して Reject する。

## 二層で判定する

### 1. Task の充足

- Given / When / Then / And をすべて満たしているか。
- 実装済み、未接続、未検証、fixture・mockによる模擬成功を区別しているか。
- 検証が型チェックやbuild成功だけでなく、変更した振る舞いを確認しているか。
- 要件の一部を後続対応として残したまま完了扱いにしていないか。

### 2. システム全体の整合性

変更によって追加・変更された概念を列挙し、Project の正本資料と照合する。

- Role、Principal、Human、外部サービスなどの操作主体
- Entity、状態、状態遷移、データの所有者
- API、MCP tool、CLI、Web UIなどの公開経路
- component、module、repository、実行基盤の責務境界
- 認証、認可、Credential、Projectとの紐づけ
- 冪等性、再送、timeout、retry、resume、監査・来歴

固定のアーキテクチャを前提にしない。各Projectの`AGENTS.md`と設計資料に書かれた名称・責務・境界を基準にする。

## 一時実装の扱い

次のすべてを満たす場合に限り、中間状態をAcceptできる。

- 親 Story が段階導入を許可している。
- 現在の Task の完了条件が、その中間状態を明示的に許容している。
- 恒久状態への移行条件が分かる。
- 不足を解消する Task がすでに作成され、追跡できる。

単に「後で直す予定」であることは、現在の不整合をAcceptする理由にならない。

## Accept 条件

- Task と親 Story の完了条件を満たす。
- 人と確認した要求・制約に反しない。
- Project の正本資料が定義する責務境界・用語・公開経路と整合する。
- 実際の振る舞いを示す十分な証拠がある。
- 未解決の重要な疑問や、追跡不能な不足がない。

## Reject reason の書き方

最低限、次を含める。

- 期待した状態
- 確認できた実際の状態
- 差分が受入を妨げる理由
- 再受入に必要な条件

テストが成功していても、要求またはProjectの責務境界に反する場合はRejectする。

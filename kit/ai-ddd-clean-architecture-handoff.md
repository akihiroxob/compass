## 3. 背景と問題意識

発端は「DDDやClean Architectureは人間の認知限界に対処する手法なのではないか。AIならREADME / AGENTS.mdに構造を書くだけでも十分ではないか」という問いだった。

元会話のアシスタントは、次のように整理した。

- **認知上の負担**：必要なコードの探索、依存関係の理解、文脈の保持。
- **構造上の問題**：業務ルールの重複、複数入口での検証漏れ、変更の波及、依存の混在。
- AIが多くのコードを読めても、重複したルールや不適切な依存が自動的に解消するわけではない。
- README / AGENTS.mdは構造や意図を説明する。コード上の境界、型、テスト、依存チェックは、実装がその意図に沿っているかを検証する。

したがって検討の中心は、**変更に必要な文脈を小さくし、変更箇所と契約を明示し、違反を機械的に検出できる構造**に置かれた。

これらは本会話の設計上の見立てである。元回答の星評価や研究紹介から、特定の構成がAIの成功率・トークン効率を保証すると解釈しない。本資料では研究の数値を再掲せず、外部文献の再検証も行っていない。

## 4. 設計思想の中心案

元会話での仮称は **Bounded Context First + Lightweight Clean Architecture**。

> 業務上の意味・用語の境界を先に定め、その内部でDomain / Application / Adaptersを分ける。戦略的DDDと依存制御を重視し、戦術パターンと抽象化は必要に応じて選ぶ。

| 原則案 | 狙い |
|---|---|
| 意味的な局所性 | 一緒に変更するコードを近くに置き、探索範囲を絞る |
| ユビキタスランゲージ | 境界内の仕様・会話・コードで用語を揃える |
| 明示的な境界と契約 | 内部実装と公開入口、業務ルールと外部I/Oを区別する |
| 浅い抽象化 | 目的のないInterfaceや中継クラスを増やさない |
| 実行可能な不変条件 | 業務上守るべき条件をコードとテストにする |
| 局所的な説明 | 共通ルールとContext固有の知識を分ける |
| 機械的な検証 | 型・lint・テスト・モジュール境界で違反を検出する |

補足：境界をフォルダに分けるだけで依存が制約されるわけではない。検証ルールと実行経路まで具体化する必要がある。また、Bounded ContextをAIのコンテキストウィンドウと同一視しない。前者はモデルと言葉の有効範囲であり、探索を局所化する効果が期待されている。

## 5. 採用方針の検討案

以下は元会話の提案を整理したもの。全項目が未承認の採用候補であり、網羅性を検証したDDD / Clean Architectureの全パターン目録ではない。

### 5.1 戦略的DDD

| 要素 | 元会話の提案 | 人・AIへの期待効果 |
|---|---|---|
| Domain / Domain Model | 重視する | 対象業務とルールを共有できる |
| Ubiquitous Language | 標準ルール候補 | 人の認識差と検索語の揺れを減らす |
| Bounded Context | 標準ルール候補 | モデルの責務と探索範囲を限定する |
| Context Map | 標準ルール候補 | 境界間の関係と変更の影響を把握する |
| Subdomain | 原則整理する案 | 業務領域を分解する |
| Core / Supporting / Generic Subdomain | プロジェクトに応じて整理 | 注力領域と一般的機能を見分ける |
| Domain Vision Statement | 推奨案 | 対象領域の目的を短く共有する |
| Anti-Corruption Layer / Published Language / Open Host Service | 境界連携で検討 | 外部モデルの翻訳と公開契約を明示する |
| Partnership / Customer–Supplier / Conformist / Separate Ways | 関係に応じて使用 | Context間の協調・依存・非統合を説明する |
| Shared Kernel | 安易な採用を避ける案 | 共有変更による影響範囲の拡大を抑える |
| Big Ball of Mud | 避けたい状態として紹介 | 境界不明瞭な領域を認識する |

同じ言葉が別Contextで異なる意味を持つ可能性はある。元のInstruction案の「全業務概念を一つのContextに所属させる」は、システム全体で一つの共通モデルに統一する指示として使わず、各モデルの所有境界を明確にする意図として再検討する。

### 5.2 戦術的DDD

| 要素 | 採用案・条件 |
|---|---|
| Invariant | 重視。何を常に守るかを明示し、検証する |
| Module | 業務概念でコードをまとめる |
| Entity | 同一性を追跡する必要がある場合 |
| Value Object | 値の意味・制約を表現する場合に積極検討。一律にクラス化しない |
| Aggregate / Aggregate Root | 一貫性を守る変更単位が必要な場合。単なる関連オブジェクト群にしない |
| Application Service / Use Case | アプリケーションの処理手順を明示する中心候補 |
| Domain Service | Entity / Value Object等に自然に属さない業務ルールがある場合 |
| Repository | 永続化の抽象が必要な場合。集約を使う場合は集約単位を基本とする案 |
| Domain Event | 業務上の出来事を表現・連携する必要がある場合 |
| Policy / Specification | 判断規則や再利用する業務条件を明示したい場合 |
| Factory | 生成処理が複雑な場合のみ |

元会話での評価傾向は、用語・不変条件・Use Caseを人とAIの双方に有用とし、Value ObjectやAggregateは意味が合えば有用とするものだった。Factory、過剰なInterface、共有モデルは探索・変更負担が増え得ると評価された。これは主観的な設計評価であり、実測比較ではない。

### 5.3 Clean Architecture

中心案は、フォルダ名や層数よりも**ソースコードの依存方向**を重視すること。

| 要素 | 統合・採用案 |
|---|---|
| Entities | DDDのDomain側に業務ルールをまとめる。DDDのEntityと用語を機械的に一対一対応させない |
| Use Cases / Interactors | Applicationに配置する |
| Interface Adapters | 入出力や外部モデルの変換を担う |
| Frameworks & Drivers | DB・Web・MCP等を外側で扱う |
| Dependency Rule / Boundary / Dependency Inversion | 内側を外部実装に依存させない中心原則 |
| Input Port | 必要時。Use Caseごとの重複Interfaceは必須にしない |
| Output Port | 外部機能への要求を契約化する場合に使用 |
| Controller / Presenter / Gateway | 入力・表示・外部接続の必要に応じて配置 |
| DTO / Boundary Model | 境界を越える契約を明示する。形式だけの重複モデルを増やさない |
| Composition Root | 実装の組み合わせを起動・構成箇所に集約する |

依存方向の略図は `adapters → application → domain`。外向きの処理は内側のPortと外側の実装で接続する。これは実行時の呼び出し順を一方向に限定する意味ではない。

## 6. 制約・避けたい設計

### 引き継ぎ時に守ること

- 未確定事項を決定事項に昇格させない。
- 今回の資料作成を、実装・移行・AGENTS.md変更・Skill導入の承認として扱わない。
- 実装に進む場合は、既存設計・命名・テスト方針を先に確認する。
- 元会話の例を、実在する業務仕様や現在のコードの事実として扱わない。

### 元会話で避けたいとされた設計案

- 全クラスへのInterface / Implの機械的な付与。
- 単純なUse CaseへのController / Interactor / Input Port / Output Port / Presenterの一律展開。
- `GenericRepository<T>`やFactoryを、具体的な必要性なしに導入すること。
- `Manager` / `Helper` / `Utils`等の曖昧な名前に責務を集めること。
- 所属するContextを考える前に、業務概念を`shared`へ移すこと。
- 技術分類だけで細かく分け、一つの変更で多数のフォルダを巡回させること。
- Bounded Contextの分割を、そのままマイクロサービス化の理由にすること。

これらは検討中の抑制方針であり、例外を許さない禁止事項としてはまだ採用されていない。

## 8. Instructionへの落とし込み方針

**Instructionには継続的なルールと知識を、Skillには作業の手順を置く**という分担が提案された。

| 資料 | 内容案 |
|---|---|
| `AGENTS.md` | 共通の短いルール、参照すべき資料、検証手順 |
| `docs/architecture.md` | 設計理由、層の責務、依存方向、採用・不採用の判断基準 |
| `docs/context-map.md` | Contextの関係、モデルの所有者、連携契約 |
| 各`CONTEXT.md` | 目的、用語、不変条件、集約、公開Use Case、外部依存 |

`CONTEXT.md`は参照資料として提案されたもの。ファイル名だけで自動的に読まれる前提を置かず、InstructionやSkillの手順に読み込み対象として明記する。

標準ルールとして検討する内容は次のとおり。

1. 変更対象のContextと、その中で使う用語を確認する。
2. 業務上の不変条件をDomainに置く。
3. Applicationは明示的なUse Caseとして処理を組み立てる。
4. DomainからDB・MCP・HTTP・フレームワーク・ファイルシステム・環境変数へ直接依存しない。
5. 外部依存には必要なPortを定義し、Adapterで接続・翻訳する。
6. Contextをまたぐアクセスには公開契約を使う。
7. 戦術パターンと抽象化は、業務上・技術上の必要性がある場合に導入する。
8. 不変条件とUse Caseの振る舞いを検証し、依存ルールの違反を確認する。

元会話に登場した「有効なClaimは高々一つ」等の条件も説明例である。テンプレートから実プロジェクトへ転記する際は、業務要件を確認する。

## 9. Skill化候補：元会話で提案された作業手順

以下は将来の作成候補であり、今回Skillを作成・導入したわけではない。共通の参照資料は`AGENTS.md`、設計資料、対象`CONTEXT.md`、公開契約、既存コード・テストとする。

| 名前 | 目的・発火条件 | 主な手順 | 追加参照先 | 価値 |
|---|---|---|---|---|
| `model-domain` | 新しい業務領域やルールを整理する時 | 用語・責務を確認 → 不変条件を列挙 → 境界・モデル案を作る | 要件、業務例 | 実装前の意味の混同を減らす |
| `implement-use-case` | 業務操作を追加・変更する時 | Context確認 → モデル・契約確認 → Use Case実装 → 必要なPort / Adapter → 検証 | 入出力契約 | 実装箇所と検証範囲を揃える |
| `add-adapter` | 新しい外部接続や入口を追加する時 | 契約確認 → 変換・接続実装 → 構成へ登録 → 接続の検証 | 外部API・DB等の仕様 | 外部都合が内側に漏れるのを抑える |
| `add-bounded-context` | 独立したモデル境界が必要な時 | 境界の理由確認 → 用語・契約定義 → Context Map更新 → 構造作成 | 既存Context Map | 不要な分割と境界の曖昧さを減らす |
| `evolve-domain-model` | 用語・不変条件・集約を変える時 | 影響確認 → モデル・契約変更 → 必要な移行 → テスト・資料更新 | 永続化モデル、呼び出し元 | モデル変更の漏れを減らす |
| `architecture-review` | 設計・変更差分を評価する時 | 用語・境界・依存・抽象化を確認 → 機械検証 → 指摘整理 | 差分、依存設定 | 設計評価を再現可能にする |

**必要なコマンドの方針：** 各リポジトリで既存の型チェック・lint・テスト・依存検証コマンドを確認し、Skillに記載する。現時点で言語・実行環境は未定のため、具体的なコマンド名は未確定。採用されていないツールを必須として書かない。

`implement-use-case`の元会話の手順案は、対象Contextの特定 → `CONTEXT.md`確認 → 用語確認 → Aggregate / Invariant確認 → Use Case追加 → 必要ならDomain変更 → 必要ならPort追加 → Adapter実装 → Invariant / Use Caseテスト → 依存違反確認、という順序だった。実際には既存実装や変更内容に合わせて適用する。

## 10. 機械的な検証の方針案

文書・Skill・検証設定を一式にする「Wacha Architecture Harness」という仮称も提案された。具体的な採用ツールと強制範囲は未決定。

- 内側から外側への不正なimportを検出する。
- 別Contextの内部実装への直接参照を検出する。
- 型や境界契約の整合性を確認する。
- 業務上の不変条件、Use Caseの成功・失敗条件をテストする。
- 外部接続については必要な契約・統合テストを選ぶ。

ESLint、パッケージの公開範囲、モジュール境界等は選択肢であり、採用決定ではない。静的チェックが全ての業務上の正しさを保証するとは扱わない。

## 12. 次にやること

1. **DDDの確認内容を回収する。** 別チャットの学習結果を共有してもらい、理解が曖昧な点を整理する。
2. **要素ごとの評価を見直す。** 戦略・戦術・Clean Architectureを分け、人・AIへの利点、コスト、適用条件を再評価する。
3. **最小の標準案を選ぶ。** 必須・条件付き・原則不要を、具体的な判断基準付きで定義する。
4. **代表的なサービスやUse Caseで試す。** 用語、Context、依存方向、変更対象ファイルを具体化し、過剰な分割になっていないか確認する。
5. **InstructionとSkillを具体化する。** `architecture.md`、短い`AGENTS.md`案、`CONTEXT.md`テンプレート、優先度の高いSkillから作る。
6. **検証設定を組み合わせる。** 選定スタックの既存ツールに合わせて、依存チェック・型チェック・必要なテストを整える。
7. **試行結果を踏まえて標準化する。** 効果と負担を確認し、採用ルールと例外を確定する。

Codexが次に再開するときは、まずこの資料を検討中の設計記録として読み、ユーザーのDDD確認結果と適用対象を確認する。元回答の強い表現を根拠に、全パターンを強制したり、既存サービスを一括再構成したりしない。

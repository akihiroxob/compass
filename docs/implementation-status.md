# 現在の実装状況

ソースコードと公開入口に基づく現況。移行後の設計は [Architecture Handoff](../compass-codex-architecture-handoff.md) と [ADR 0001](adr/0001-workspace-project-boundary.md) を参照する。

Workspace・Project・Projectの Repository / Resourceは`packages/organization`が所有する。Workspaceはモデル・保存・application use case（作成・参照・一覧・更新・archive、既存WorkspaceへのProject作成、所属Project一覧）を持つ。公開入口はHuman向けWeb API（作成`POST /api/workspaces`、参照`GET /api/workspaces`・`GET /api/workspaces/:workspaceId`・`GET /api/workspaces/:workspaceId/projects`、Mission等の更新`PATCH /api/workspaces/:workspaceId`、既存WorkspaceへのProject作成`POST /api/workspaces/:workspaceId/projects`、archive`POST /api/workspaces/:workspaceId/archive`。作成以外はWorkspace Membershipで認可）と、それを使うWeb UIのWorkspace Selector・Shell・作成/編集/Project追加/archiveの導線（[Web UIのShell](#web-uiのshellとworkspace-selector)）と、Workspace「設定」のmember・Direction Role Grant・Workspace Credentialの管理（[Workspace設定](#workspace設定web-ui)）で、Workspace管理のMCPは無い。Projectの参照（Web API・MCP・Role Context）は所属`workspaceId`を返す。全Projectは1つのWorkspaceに所属し（`project.workspace_id`）、Mission・Vision・Principles・Constraintsの正本は所属Workspaceである。Projectの応答（Web API・MCP・Role Context）は所属WorkspaceのMission等を参照値として含む。`POST /api/projects`・MCP `create_project`は戦略値を持つ専用のWorkspaceを同じtransactionで作る（Web UIからの導線は無く、Web UIは既存WorkspaceへのProject追加を使う）。Projectの更新（`PATCH /api/projects/:projectId`・MCP `update_project`）はname・purpose・Repository・Resourceだけを受け取り、Mission等は受け取らない（未知の項目として無視し、Mission等だけの入力は`VALIDATION_ERROR`）。Mission等はWorkspace Membershipのadministrator以上がWorkspaceの更新で変更し、Project Roleでは変更できない。Projectのarchiveは所属Workspaceの状態を変えない（最後のactive Projectでも同じ）。WorkspaceのarchiveはWorkspace ownerだけが`POST /api/workspaces/:workspaceId/archive`で行い、Project RoleからはWorkspaceを停止できない。archivedのWorkspaceは更新・Project作成を拒否する（`CONFLICT`・`workspaceStatus: archived`）。archivedのWorkspaceに所属するactiveなProjectは、Projectの項目を更新できる。`project`は所属`workspace_id`（NOT NULLのFK）・name・purpose・状態だけを持ち、Mission等の列・`project_principle`・`project_constraint`は無い。schemaは新規DBの定義だけで、旧DB向けの列追加・戦略値の変換・Membershipの補完は行わない（開発DBは再作成する）。Workspace自体の作成・archiveはActivityを記録しない。Intent・Outcome・成功条件はWorkspace所有で、`intent.workspace_id`・`outcome.workspace_id`へ保存する。Active IntentはWorkspaceにつき最大1件、OutcomeとIntentのWorkspace一致は複合FKで強制する。Intent/Outcome/Research/Decision/ADR/Evaluation/Runtimeのapplication use caseとRepositoryはWorkspace IDを直接受け取り、serverの内部`workspaceDirection`へ組み立てる。Workspace Directionの公開入口（Web API `/api/workspaces/:workspaceId/…`・MCP toolの`workspaceId`入力・Strategist / Researcher / Evaluator Context）は接続済みで、HumanはWorkspace Membership、AgentはWorkspace Role Grant（Workspace Agent Credential）、Runtime eventはWorkspace Runtime Credentialで認可する。Workspace Role Grantの付与・取消・一覧はWorkspace Membershipで認可するHuman向けWeb API（`/api/workspaces/:workspaceId/grants`）とWorkspace「設定」に接続済みで、MCPには公開しない。Agent / Runtime CredentialはWorkspace / Projectの明示scopeで保存・認証し、Workspace Credentialの管理はWeb API（`/api/workspaces/:workspaceId/credentials`）とWorkspace「設定」に接続済み（[Credential](step-6-human-auth-design.md#agentruntime-credential)）。新規Project GrantはManager・Worker・Reviewerとtrusted-local用`runtime`だけを受け付け、Workの参照・更新もExecution Roleだけを認可する。Direction activeRoleと旧Direction/Runtime GrantによるWork参照を拒否する（[Agent認可](step-4-strategist-role-design.md)）。Project配下のDirection経路とMCPの`projectId`入力は廃止し、Project IDをWorkspace IDとして解釈しない。Project Membership・Project Grant・Project CredentialからWorkspace Directionは継承しない。Execution Summary/EvidenceだけはProject固有の記録としてProjectの入口（Project Membership・Project Runtime Credential）に残る。Story作成時のOutcome参照は、Projectの所属Workspace・Constraints・Repository（Project execution context）と所属WorkspaceのOutcome snapshotを読み、そのProjectがOutcomeのTargetであることを検査する（Target外は`CONFLICT`・`reason: not_target_project`）。ManagerはProject manager Grantだけで、MCP `get_outcome_handoff_context`からTargetのOutcome本文・成功条件を読む（Workspace Direction Grantは継承しない）。Project基準のOrchestration State（`get_orchestration_state`）は除き、Orchestration StateはWorkspace単位だけとした。Workspace単位の`get_workspace_orchestration_state`（S08-01）はWorkspace Runtime Credentialで公開済みで、OrchestratorはこれをWorkspace Runtime Credentialで読み、dispatch規則（`planWorkspaceDispatches`、S08-02）でWorkspace Role・Target ProjectのmanagerをscopeごとのAgent Credential設定で起動する（S08-03）。Intent/Outcome/Research/Decision/Evaluation/Runtime eventの応答は`workspaceId`を持ち、`projectId`は持たない。Research Request/Result/Finding/Evidence/Synthesis・Direction Decision・ADR依頼/参照はWorkspace所有へ切替済み。Research/Decisionは`workspaceId`だけ、ADRは対象artifactの`projectId`・`repositoryId`も保持する。Evaluation・Runtime eventは`workspaceId`だけで保存・取得し、Execution Summary/Evidenceは`workspaceId`と発生元`projectId`を併せ持つ。SummaryはOutcome・Projectごとに1行、Evidenceの一意性はOutcome・Project・種別・URI・versionで保つ。Accessの公開Role Grant（付与・取消）は、Execution RoleをProject、Direction RoleをWorkspaceの入口で扱う。OrchestratorはWorkspace単位で動作する。Runtime eventとWorkspace Orchestration Stateの入口はWorkspace Runtime Credential、Execution change・Evidence・SummaryはProject Runtime Credentialで認可する。CredentialはWorkspace / Projectの明示scopeに束縛し、互いに転用できない。Directionのcanonical ActivityだけはWorkspace単位、Work・Project archive・明示Activityは所属Workspace付きProject単位で保存する。

Research Request / Result / Finding / SynthesisとDirection Decision・Evaluationは現在DBに保存する。Intent作成はResearch Requestを作らず、OrchestratorがStrategistを起動してResearchの要否を判断させる。保存先は内容と所有責務で個別に判断し、Project別であることや本文が長いことを理由に一律移行しない。

現在のExecution Role名は`manager` / `worker` / `reviewer`で、統合後も維持する。

Intent/Outcomeの状態変更・成功条件・canonical Activityは同じtransactionで確定し、通知保存に失敗すれば全て巻き戻る。serverの`directionChangeObserver`はActivity投影に加え、`outcome_confirmed`・`research_requested`・active IntentのResearch確定に対応する`research_completed`をWorkspace Runtime eventへ投影する。Projectが無い、または複数あるWorkspaceでも保存する。Evaluation・`outcome_evaluated`・Workspace Activityも同じtransactionで確定し、失敗時は全て巻き戻る。eventのversionは2、配送・ackはWorkspaceとconsumerで取得・保存する。Runtime eventの公開入口（`fetch_runtime_events` / `ack_runtime_event`、`/api/workspaces/:workspaceId/runtime-events`）はWorkspace Runtime Credentialで認可して接続済み。OrchestratorはWorkspace単位の現在状態で起動し（S08-03）、実Agentによる自律実行は未検証。

Research/Decision/ADRのWorkspace契約と、Contextの件数上限・Resource参照・公開入口は[Research・Decision・ADR](research-decision-adr-design.md)を参照する。`server/tests/workspaceResearch.test.ts`は新規file DBの再起動・version/根拠/ADR参照の保存、別Workspace・archive拒否、Resource所属、Activity rollback、Context省略、共有WorkspaceのWorkspace ID・Workspace Grantによる公開とProject ID・Project Grantの拒否を検証する。実Agentの自律運転は未検証。

Evaluation/Execution/Runtimeの内部Use Caseは`workspaceDirection`へ配線済み。Outcomeの評価可能性はDirectionの`assessOutcomeEvaluability`が全Target（設定順）の還流状況から判定する。`evaluable`は全TargetからSummaryが還流し`incomplete`が無い場合だけで、一部Projectの完了だけでは評価しない。`no_targets`（Targetなし）と`replan_required`（archived Targetに未還流または`incomplete`が残る）はStrategistの判断対象、`awaiting_execution`はactive Targetの還流待ちで、`unfinishedTargets`に評価を妨げるTargetのProject ID・状態・理由（`not_reflected` / `incomplete`）を返す。archive前に完了を還流したTargetは、Project archiveだけを理由に評価から除外しない。Target解除前に還流された記録（`nonTargetExecutions`）は評価可能性・評価の根拠に含めない。Evaluator Context（`get_evaluator_context`）は`targets`（Target別の`projectStatus`とSummary・Evidence。未還流はnull）と`evaluability`を返し、`list_outcome_target_executions`・`/target-executions`も同じ`evaluability`を返す。`record_outcome_evaluation`は`evaluable`以外を`CONFLICT`（`reason`に状態、`unfinishedProjectIds`）で拒否し、保存と同じtransactionで現在の全Target・Projectの状態・Summary/Evidenceを読み直してsnapshotと照合する。評価中のTarget追加・解除や還流で食い違えば評価・`outcome_evaluated`・Activityを保存せず、最新の状態から判定し直す（変わり続ければ`reason: targets_changed`）。Evidence根拠はいずれかのTargetが還流した参照に限る。Evaluation snapshotは全Targetの`projectId`・`projectStatus`・Summary・EvidenceをProject別に保持し、合算しない。Workspace単位の`get_workspace_orchestration_state`はOutcomeごとにTarget別の`projectStatus`・Work件数・還流状態と`evaluability`を返し、`no_targets` / `replan_required`のOutcomeを状態だけで識別できる。Orchestratorの`planWorkspaceDispatches`（S08-02）はこれらをWorkspaceのStrategistへ、`evaluable`をEvaluatorへ、active TargetでStory / Taskの無いProjectをそのProjectのmanagerへ割り当てる（archivedのProjectのmanagerは起動しない）。Orchestratorの周回はこの規則で起動する（S08-03）。Evaluationの公開入口（`get_evaluator_context` / `record_outcome_evaluation`・`/api/workspaces/:workspaceId/outcomes/:outcomeId/evaluations`）はWorkspace Role Grant・Workspace Membershipで認可する。Execution Summary/Evidence（`get_outcome_execution_summary` / `record_execution_evidence`・`/api/projects/:projectId/outcomes/:outcomeId/execution-summary|execution-evidence`）はProject固有の記録として、Project Runtime Credential・Project Membershipで認可し、所属Workspaceを明示して読む・還流する。

`server/tests/workspaceExecutionDirection.test.ts`は新規DBでProject別Summary/cursor/Evidence、複合FKによるOutcome/Intent/Project/event/delivery/ackのWorkspace一致、評価・イベント・Activityのrollback、archiveガード、同じschemaでのfile DB再初期化と評価・ack再送を検証する。旧DBの変換は行わず、開発DBを再作成する。Execution SummaryのProject入口とEvaluation・Runtime eventのWorkspace入口の分離（Project Grant・trusted-localのAgent名から継承しない）も同テストで検証し、各入口の契約・認可は既存のExecution/Evaluation/Runtimeテストで回帰検証する。HTTPは`app.request`またはMCPのテスト呼出であり、実Agentの自律運転を示すものではない。

`server/tests/multiProjectOutcomeEvaluation.test.ts`は新規file DBで、同じWorkspaceのTarget A / BそれぞれのManager・Worker・Reviewer（Project Grant）によるTask受入、Runtimeの還流、Evaluator・Strategist（Workspace Grant）の判断をMCP・Web APIで通す。Aだけの受入では評価を`CONFLICT`（`awaiting_execution`・`unfinishedProjectIds`にB）で拒否してEvaluation・`outcome_evaluated`・Activityを作らず、Evaluator Context・`list_outcome_target_executions`・`/target-executions`から欠けているTargetを辿れる。Evidenceを還流していないTargetの成功条件は`insufficient_evidence`となり、Project別snapshotとStrategist Contextで根拠と欠落Targetを辿って追加Research・次のOutcome（`failed`）・Intent完了（`achieved`）へ接続する。評価・判断の再送と同じschemaでの再起動後の再送は保存済みの結果を返す。単一TargetのOutcomeは他Projectのある同じWorkspaceでもそのTargetだけで評価できる。既存の単一Project Outcome・再送・再起動の契約は`outcomeEvaluation.test.ts`・`evaluationReplan.test.ts`・`lv6ClosedLoop.test.ts`で回帰検証する。

## Role / Skill Contextの現行契約

構成資産はrepo直下の`roles/<role>.md`（frontmatterの`skills`で使うSkillを参照）・`policies/role-policy.md`・`skills/<name>.md`（frontmatterに`requiredKnowledge`とnamespace付きの`requiredTools`。`allowRoles`は持たない）・`knowledge/`（Agent System共通知識）に置く。serverの`FileAgentAssetRepository`（infrastructure）がfileとGit revisionを読み、`AgentContextService`と、Project Role向けの`GetRoleContextUseCase`・Workspace Role向けの`GetWorkspaceRoleContextUseCase`（`server/src/application/agentContext`）が配信する。Role Contextはscopeごとに別toolとし、`projectId` / `workspaceId`を任意入力で切り替えない。

- `get_role_context({ projectId, role })`: Project Role（manager / worker / reviewer）のContext。ProjectのそのRoleのGrantが必要（activeRole指定時は同じRoleに限る）。Role Definition（frontmatterを除いた本文と`skills`）・共通Policy・参照Skillのmetadataと、Project（`id`・`workspaceId`・`name`・purposeの`description`・`status`）・Project Resources・所属Workspaceの要約（`workspace`。Mission / Vision / Principles / Constraints / status。戦略値の正本はWorkspaceで`project`には重複させない）・関連Outcome（`outcomes`。このProjectを現在TargetとするactiveなOutcomeだけを、Target設定の新しい順に`id`・`intentId`・`title`・`description`・`hypothesis`・`status`・固定Success Criteria・関連Storyの`correlationId`）・最近のProject Activity（`activity`。`list_activities`と同じ形で新しい順に最大20件、summaryとrefsだけ）を返す。他Project・Target外・取消/評価中等activeでないOutcome・Workspace Activity・別Workspaceの情報、Skill本文・Knowledge本文・Activity本文は含めない。`unavailable`は空配列。`get_strategist_context`・`get_outcome_handoff_context`等の集約は置き換えない
- `get_workspace_role_context({ workspaceId, role })`: Workspace Role（strategist / researcher / evaluator）のContext。WorkspaceのそのRoleのGrantが必要（activeRole指定時は同じRoleに限る。Project Grant・旧Project Direction Grantは数えない。Grantの検査はWorkspaceの存在確認より先で、別Workspace・存在しないWorkspaceは`FORBIDDEN`）。`role`はWorkspace Roleだけを受け付ける。Role Definition・共通Policy・参照Skillのmetadataと、Workspace（Mission / Vision / Principles / Constraints / status）・activeなProjectの要約（`projects`。更新の新しい順に`id`・`name`・purposeの`description`・`status`・Repository / Resourceの参照）・最近のWorkspace Activity（`activity`。`list_workspace_activities`と同じ形で新しい順に最大20件、summaryとrefsだけ）を返す。Story / Task等のProject Work・Project Activity・archivedのProject・別Workspaceの情報、Skill本文・Knowledge本文・Activity本文は含めない。`unavailable`は空配列。`get_strategist_context`等のDirection集約は置き換えない
- `list_skills({ status?, role? })`・`get_skill_context({ name })`: 静的な手順書の取得でGrantは不要（remote modeの匿名呼出しには公開しない）。`role`は認可ではなくRole Definitionの参照による絞り込み
- 各応答の`source`は資産を読んだHEADの`revision`と、資産directoryの未commit変更の有無`dirty`（Git管理外はnull）
- 資産の欠落・形式不正（`allowRoles`・namespaceなしのTool・未知のSkill参照・knowledge外のpath）は部分応答を返さず`INSTRUCTION_UNAVAILABLE`。未知のSkillは`NOT_FOUND`
- `get_role_instructions`は互換のため残し、`policies/role-policy.md`（`includeShared`時に先頭）と`roles/<role>.md`をfileのまま返す

## Activityの現行契約

`packages/activity`がActivity（`activity` table）を所有する。追記専用で、更新・削除の経路は持たない。Change Log（Work）・Runtime event（Direction）・Operational Log（stdout）とは別のtableと契約で、Agentの実行単位（`runId`）は持たない。

- 項目: `id`・`cursor`（全体で単調増加）・`scope`（`system` / `workspace` / `project`）・`workspaceId`・`projectId`（DBのCHECKでsystemは両IDなし、workspaceはWorkspace IDのみ、projectは両ID必須。FKで各IDの存在を検証）・`type`（`research.summary`等のdot区切り小文字）・`principalId`・`role`・`summary`（必須、500文字以内）・`body`（任意のMarkdown）・`refs`・`correctsActivityId`・`source`（`recorded` / `canonical`）・`occurredAt`・`recordedAt`。
- `refs`: `project_resource`（Projectに登録済みのRepository・Resourceの`resourceId`と任意の`path`・`revision`）・`url`（http(s)）・Entity（`intent`・`outcome`・`research_request`・`decision`・`story`・`task`・`activity`のid）。成果物の本文は持たない（未知の項目は拒否）。

## Executionの現行契約

Organizationが所有するProjectを実行境界として共用し、Execution専用のProjectを複製しない。`packages/work`がStory / Task / Claim / Review / Acceptanceを所有する。状態遷移・Claimの排他と期限・自己レビュー / 自己受入の禁止はapplication層（`TaskCoordinationService`）が持ち、保存は`WorkStore` port（Kysely実装は`packages/work/src/infrastructure`）を通す。

Outcomeを参照するStoryは、成功条件・Constraints等の作成時snapshotと相関IDを持つ。相関IDとTaskの`taskKey`によって再送を同じ作業へ収束させる。Work側の受入をOutcome達成とは扱わない。

HumanはExecution一覧・Task詳細・最近の変更を参照でき、editor以上は手動起票・編集・受入・差戻し・取消・Commentを行える。Outcome handoffで管理するStory / TaskはHumanから編集できない。Story / Taskの編集（Web UI・MCPの`edit_story` / `edit_task`）は、内容が変わった場合だけ同じtransactionで`STORY_EDITED` / `TASK_EDITED`をChange Logへ追記し、`payload.changes`に変更前後を残す。MCPの同一`requestId`再送・失敗した編集では記録しない。編集は「最近の変更」とTask詳細の変更履歴に表示する。有効Claimとの競合を拒否し、取消後の古いClaim操作も拒否する。

Project詳細の「Claim保持中」は、既存の`execution`の`activeClaim`だけから、期限内のClaimを持つAgent・Taskを作業中・レビュー待ち・受入待ちに分けて出し、Task詳細へリンクする。期限切れ（`reclaimable`、または表示中に期限を過ぎたClaim）は保持中に含めず、`doing`のTaskを再取得待ちとして件数で出す。取得時刻と再読込を出し、読込中・取得失敗・Claim無しを区別する。Claimは作業権の期限付き保持で、Agentプロセスの稼働を示さない。Role割当・Credentialからは担当を推測せず、Claimを持たないStrategist・Researcher・Evaluatorの状態は出さない。

DirectionとWorkは公開index（`@compass/direction`・`@compass/work`）とapplication portで接続し、DirectionはWorkに依存しない。WorkはProject状態・Role Grantを`WorkStore`の読取port（`ProjectStateReader`・`ProjectGrantReader`）で、Claim・状態遷移と同じtransactionの中で読む。実装はserverが配線し（`server/src/infrastructure/repository/contextAdapters.ts`）、Workは`project`・`project_grant`のtableを直接扱わない。Directionのuse caseが要求するRole・Runtime scopeの認可も、Directionのportへserverの認可serviceを渡す。境界は [executionBoundary.test.ts](../server/tests/executionBoundary.test.ts) で静的に検証する。Workの規則の単体テストは`packages/work/tests/`、Workspace・Projectの単体テスト（Project作成・更新・archive、Mission等のWorkspaceへの読書き、新規DBの`project`定義と再初期化）は`packages/organization/tests/`にある。Direction固有のpackage単体テストは無く、Directionの振る舞いは`server/tests/`で検証する。

- 参加中のProject（`/projects`）はProject Membershipを持つProjectをWorkspaceをまたいで一覧する。Projectの作成はWorkspaceのProject追加から行い、`/projects/new`は無い。Projectの編集はname・purpose・Repository・Resourceだけで、Mission等は所属Workspaceの概要への導線を出す。
- ナビゲーションのリンクはProject詳細のview切替と同じ`nav-link` mixin・tokenを使い、tokenの変更は双方へ反映する。

## Workspace設定（Web UI）

Workspaceの「設定」（`/workspaces/:workspaceId/settings`。`features/workspace/WorkspacePages.tsx`の`SettingsContent`）は、Workspace scopeのHumanとDirection Agentを管理する。導線の表示はWorkspace Membershipの`myRole`と権限表`humanWorkspacePermissions`で決め、拒否は常にserverが行う。Project RoleからWorkspaceの権限を、Workspace RoleからProjectの権限を継承しない。

- Member（`features/member/WorkspaceMembershipSection.tsx`）: 一覧はviewer以上。ownerだけにRole変更・取消（確認パネル）と追加を出す。追加は`GET /api/workspaces/:workspaceId/member-candidates`の候補（所属ProjectのMemberで、このWorkspaceのMemberでないHuman）から選び、emailでのHuman検索は無い。最後のownerは導線を無効にする（serverも`409 LAST_OWNER`）。Memberの追加・取消のたびに候補を取り直す。追加・Role変更・取消はProject Membershipを変えない。
- Direction Agent（`features/grant/GrantSection.tsx`の`AgentSettingsSection`をWorkspace scopeで使う）: Strategist・Researcher・Evaluatorごとに割当済みAgentを出す。付与・取消はadministrator以上、一覧はviewer以上。Execution Role（Manager・Worker・Reviewer）は出さない。付与時は別scope（別のWorkspace・Project）の有効なAgent Credentialに束縛されたAgent名だけを`409 PRINCIPAL_BOUND_ELSEWHERE`で拒否し、入力を保ったまま理由を出す。別scopeのGrantだけを持ち、Agent Credentialの無いAgent名への付与は拒否しない。administrator以上には、同じWorkspaceの有効なAgent Credentialの有無を出す。
- Agent・Runtime Credential（`features/credential/CredentialSection.tsx`をWorkspace scopeで使う）: administrator以上だけに一覧・発行・rotation・取消を出し、それ以外のRoleには管理者が行う旨だけを出す。tokenは発行・rotationの応答で一度だけ表示し（`Cache-Control: no-store`）、一覧・再読込後は表示しない。発行時は別scopeのRole Grantまたは有効なAgent Credentialを持つPrincipalを`409 PRINCIPAL_BOUND_ELSEWHERE`で拒否する。Runtimeのscope選択肢はWorkspaceの入口で使う`runtime:event:read`・`runtime:event:ack`・`runtime:state:read`だけ。
- Projectのアクセス: ProjectのMember・招待とExecution RoleのGrant・Credentialは各Projectの「設定」で管理する。Project Membershipのある所属active Projectだけをリンクにし、無いProjectは開けない理由を出す。
- archivedのWorkspaceでは、Memberの追加・Role変更・取消、Direction Role Grantの付与・取消、Credentialの発行・rotationの導線を出さない（serverもWorkspaceの`409`で拒否する）。Credentialの取消はarchivedでも行え、有効なCredentialには取消の導線を出す（[Credential](step-6-human-auth-design.md#agentruntime-credential)）。
- `server/tests/workspaceSettings.test.ts`はWeb API（member・候補・Grant・Credential一覧）の権限差、Project Membership・Project Grantとの非継承、`LAST_OWNER`・`ALREADY_MEMBER`・`PRINCIPAL_BOUND_ELSEWHERE`、archive、secretの非露出、新規file DBの再初期化後の取得を検証する。`server/tests/workspaceSettingsUi.test.ts`は画面の判定・pathとerror表示を検証する。

## Project詳細（Web UI）

Project詳細は`?view=`で「概要」（`overview`。既定・不正値も概要）・「方向」（`direction`）・「実行」（`work`）・「判断待ち」（`consultations`）・「記録」（`records`）・「設定」（`settings`）に分け、表示中のviewのsectionだけを読み込む。Hero（名前・状態・自分のRole）とarchivedの通知は全viewに出し、view切替（`nav`、選択中に`aria-current="page"`）は上端へstickyにする。他viewのTask・Role行へは`?view=work#execution-task-…`・`?view=settings#agent-role-…`で辿り、読込後に移動してfocusする。decodeできないhash（例 `#%`）は無視し、viewを通常どおり表示する。

- 概要（S10-03。`features/project/ProjectOverview.tsx`、判定は`overview.ts`）: Projectを実行境界として、実行境界・貢献するOutcome・実行状況・次の行動・Claim保持中・最近の記録を出す。部分ごとに取得失敗・空・閲覧不可を区別し、取得時刻と再読込を出す。HeroのPurpose（description）は概要では実行境界へ移す。
  - 実行境界: Purpose（未設定ならProjectの編集への案内）と、Repository・Resourceの外部リンク。Mission等とIntent・Outcomeは所属Workspaceのものと示し、Workspace Membershipで閲覧できれば所属Workspaceの方向へのリンクを出す。
  - 貢献するOutcome: 所属WorkspaceのActive Intent配下のActive Outcomeのうち、このProjectがTarget Projectのもの。取得はWorkspaceの概要・方向と共有の`loadDirection`（`GET .../intents/:intentId/outcome-target-work`、Outcomeごとの`target-executions`・`evaluations`、Active Intentの`decisions`）。Outcome名はWorkspaceのOutcome詳細へ辿り、評価の段階（Workspaceの概要と同じラベル）、このProjectのWorkの段階・Story件数・Task状態別件数、このProjectのStory（`execution`の`outcomeId`で照合。「実行」viewの該当Storyへ辿る）を出す。ほかのTarget ProjectはWork・Story・名前を出さず件数だけにし、詳細はOutcome詳細で見る。Taskの受入はOutcomeの達成ではないと明示する。Workspace Membershipが無い場合は閲覧できない旨と理由を、Active Intentが無い・Targetではない（Strategistの判断）・Target別Workを取得できない（貢献か断定しない）を区別して出す。
  - 実行状況: `execution`のTaskを未着手・作業中・再取得待ち・レビュー待ち・受入待ち・差戻しの1区分ずつと受入済みに数え、未完了のStory（先頭5件。StoryごとのTask区分件数）から「実行」viewの該当Storyへ辿る。完了・取消のStoryは件数だけ。
  - 次の行動: 「あなたの操作」（最大3件。期限内Claimの無い受入待ちの確認（Editor以上）、担当待ちに対する未割当のManager・Worker・Reviewerの割当（administrator以外は依頼先）、administratorにはCredentialの無い割当済みAgent）と、「Agentの担当待ち」（貢献OutcomeのこのProjectのStory起票待ち・Task分解待ち（Manager）・Workは終わったが未還流（Runtime）、期限内Claimの無い未着手・差戻し・再取得待ち・レビュー待ち・受入待ちのTask）。Outcomeの担当待ちはWorkspaceの要対応（`planWorkspaceAttention`）と同じ規則で、最新Evaluationが判断済みのOutcomeには起票・分解待ちを出さない。Intent・Outcomeの登録、Target、評価・判断はWorkspace scopeのため出さない。還流・評価の状態やTargetを確認できないOutcomeは担当待ちを判定せず件数と再読込を出し、WorkspaceのDirectionを閲覧できなければTaskの担当待ちだけを出す。archivedでは出さない。実行状況と次の行動は、Claim保持中と同じく表示中にClaimの期限を過ぎた時点で再判定する。
  - 最近の記録: Project Activityの新しい5件（`GET /api/projects/:projectId/activities`）と「記録」viewへの導線。Workspace概要の最近の記録と同じ`RecentActivityList`を使う。
- 方向: Mission・Vision、Intent（Active Outcome・過去のIntent）、Principles・Constraints。
- 実行（S10-04。`features/execution/ExecutionSection.tsx`、判定は`execution.ts`）: Story・Task一覧、起票の導線、最近の変更。Taskが1件以上あれば「すべて」と「Humanの判断待ち」（Task詳細の受入・差戻し導線と同じ判定。レビュー待ち・受入待ちで期限内Claimが無いTask）の絞り込みを件数付きで出し、`?tasks=decision`で表す（再読込・共有・戻るで同じ一覧）。該当が無ければその旨を出す。
- Task詳細（S10-04。`features/execution/TaskDetailPage.tsx`・`TaskOutcomeSection.tsx`）: 現在位置（Workspaceを閲覧できる場合はWorkspace・WorkspaceのProject一覧、Project、「実行」viewの該当Task、Storyの該当card）を出す。Claimは保持者・期限（相対表示）と、期限付きの作業権でありAgentプロセスの稼働状態を示さない旨を出す。「Task受入とOutcome評価」でTaskの状態（Project）とStoryのOutcomeの評価（Workspace）を分けて出し、Taskの受入をOutcomeの達成として示さない。Outcome名は所属WorkspaceのIntent配下から探してWorkspaceのOutcome詳細へ辿り、評価の段階は`outcomeLoopStage`（未還流・未評価・評価済みの結果）で出す。Evidenceは、このProjectからそのOutcomeへ還流したExecution SummaryとEvidence参照（`execution-summary`。Project Membership）で、Task単位ではないと示す。評価・Outcome名は、Workspace Membershipが無い場合は閲覧不可、取得に失敗した場合は失敗として出し、未評価として扱わない。Outcomeを参照しない（手動起票の）TaskはOutcome評価の対象外と示す。受入・差戻し・取消・Commentは既存のWeb API（`/api/projects/:projectId/tasks/:taskId/…`）とUse Caseで行い、成功後はserverから読み直す。受入の通知で、Outcomeの達成は別途評価されることを示す。
- 判断待ち（`features/consultation/ConsultationSection.tsx`、判定は`consultation.ts`）: AgentがMCPで登録したProject相談の一覧（Workspaceの「判断待ち」も同じ部品でWorkspace相談を出す）。`?status=`で状態を絞り込み（既定はHumanの判断待ち。Agentの応答待ち・解決済み・取消・すべて）、再読込の導線を出す。閲覧できる全scopeの横断一覧（`/consultations`）への導線を添える。相談詳細（`/projects/:projectId/consultations/:consultationId`・`/workspaces/:workspaceId/consultations/:consultationId`。`ConsultationDetailPage.tsx`）は質問・進めない理由・選択肢・推奨・影響・参照・方針変更元、結論（判断の由来・根拠の会話・記録主体）または取消の理由、会話（Humanの発言とAgentの発言を帯の色と文言で区別）を出し、editor以上に返信、administrator以上に「この方針で決定」・取消の導線を出す（archived・解決済みでは出さない）。開いている間は15秒ごとに読み直す。Project相談の詳細は、相談を待つTaskの状態と、結論からの文書反映（反映状況・文書反映Task・成果物参照）を`ConsultationFollowupSection.tsx`で出す。
- 記録: Activity（種別の絞り込み・所属Workspaceの記録への導線。[Activityの現行契約](#activityの現行契約)）、Research、ADR参照、Repositories・Resources。
- 設定: Agent（6 Roleを1つの一覧にし、行を開くと割当・取消。administratorには割当済みAgentのCredentialの有無）、Credential（administratorのみ）、Member・招待、Projectの編集・アーカイブ。

状態badgeは意味ごとのtone（`server/src/web/statusTone.ts`）で色を分ける。要対応（受入待ち・差戻し・評価の未達成・成功条件を満たさない）は塗りのアクセント、待機（未着手・未評価・Execution未接続・受諾待ち）は枠線、進行中（作業中・レビュー待ち・Active・Execution中）は青、完了（受入済み・達成・満たす・有効なCredential）は淡い緑、終了・分類ラベル（取消・過去のIntent・Activityの種別等）は控えめ、警告（期限切れClaimの作業中・再取得待ち・Evidence不足・期限切れ）は淡い赤の枠線にする。色は`styles/_tokens.scss`の`--tone-*`で定義し、文字と背景はWCAG AA（4.5:1以上）を満たし、badgeには常に状態のラベルを併記する。動きはview切替と`details`展開の短いfade（約180ms）とbadge色の変化に限り、Claim保持・Role割当に点滅・脈動・回転・カウントダウンを使わない。`prefers-reduced-motion: reduce`ではanimation・transitionを止める。

Web UIのstyleはSass（SCSS）で、入口`server/src/web/app/main.scss`から共有（`styles/`の`_tokens`・`_base`・`_layout`）→基本部品（`components/ui/`）→組合せUI（`components/`）→app→各Featureのpartialの順に読み込み、各partialは自分の所有するclassだけを定義する（配置と検査は[Web UIの構成](web-ui.md#style)）。共通値はtokenで定義し、共通の型は`styles/_mixins.scss`のmixin（narrow・focus-ring・control-size・caps-label・panel・list-item等）で再利用する。文字色は背景（paper・surface・raised・note）に対して4.5:1以上、入力欄の枠と焦点表示は3:1以上とする。Tailwind等のutility CSSは使わない。

空状態・読込失敗・未定義URLの表示はWeb UI共通とする。空の一覧は誰が登録・起票するか（Strategist・Researcher・Manager等）を示し、Humanが登録できない場合（archived・権限なし）は導線の代わりに理由と依頼先を出す。読込失敗は、存在しない・閲覧権限の無い対象を画面ごとの文言で、接続失敗・サーバー障害・解釈できない応答をサーバーの英語文言ではなく再試行の案内で示す（`server/src/web/api.ts`の`classifyError`・`loadFailureMessage`）。未定義のURLはログイン後に404画面を出し、ホームと、Compass内から遷移してきた場合だけ直前の画面へ戻る導線を出す。

## Accessの現行契約

`packages/access`がAgentのRole Grant・Credential、HumanのProject Membership・Workspace Membership・招待・Session・ログイン試行を所有し、認可（`ProjectAuthorizationService`・`RuntimeAuthorizationService`・`HumanProjectAuthorizationService`・`HumanWorkspaceAuthorizationService`）を提供する。Human Membership・Agent Grant・Runtime Credentialのscopeは別のモデル・tableで扱う。Credentialは`{ kind: workspace | project, id }`のscopeを持ち、`RuntimeAuthorizationService`は操作対象のscopeとの一致を検査する。`server/tests/workspaceCredential.test.ts`で新規DB・file DB再初期化・scopeのCHECK/FK・管理権限・scope間の転用拒否・Principal束縛・失効・archiveを確認する。

Workspace Membership（`workspace_membership`）はProject Membershipと同じRole（owner / administrator / editor / viewer）で、Workspaceの閲覧（viewer）・Direction管理（editor）・Mission等の更新と既存WorkspaceへのProject作成（administrator）・archiveとmember管理（owner）を権限表`humanWorkspacePermissions`で認可する。未所属・取消済み・存在しないWorkspaceは404、Role不足は403。最後のownerの降格・取消は`LAST_OWNER`、archivedのWorkspaceへのMembership変更・Project作成は`CONFLICT`（`workspaceStatus: archived`）で拒否する。Project MembershipとWorkspace Membershipは相互に継承しない（Workspace memberでもProjectのWorkは操作できず、Project memberでもWorkspaceは操作できない）。memberの追加対象は、そのWorkspaceに所属するProjectの有効なMemberだけ（emailでのHuman検索は公開しない）。初期memberは、Actor付きのWorkspace・Project作成で作成者をownerにする（既存WorkspaceへのProject作成ではProjectのownerだけ）。owner不在のWorkspaceは、owner不在Projectと同じくplatform ownerのログイン時に補完する。use caseはserverの`createApplicationServices`の`human`へ配線済み。Web APIはWorkspaceの作成（ログイン済み）・参照（一覧・詳細と`myRole`・所属Project一覧。viewer以上）・Mission等の更新と既存WorkspaceへのProject作成（administrator以上）・archive（owner）を公開し、所属Project一覧はpurpose・Repository・Resourceの参照を返す（Mission等はWorkspaceの応答を参照し、Projectごとに複製しない）。Workspace memberは所属Project一覧を見られるが、Project詳細・WorkはProject Membershipで認可する。member管理（一覧はviewer以上、追加候補・追加・Role変更・取消はowner）とWorkspace Direction Role Grant（一覧`grant.read`はviewer以上、付与・取消`grant.manage`はadministrator以上）のWeb APIを接続し、Web UIはWorkspace「設定」から使う（[Workspace設定](#workspace設定web-ui)）。Direction（`/api/workspaces/:workspaceId/…`）の参照・変更はWorkspace Membershipで認可し、Project画面は所属Workspaceの状態と`myRole`で変更導線を決める（Projectのarchive後は再取得する）。Claimの所有・期限・状態遷移・自己レビュー / 自己受入の禁止はWorkが強制し、Accessへ移さない。transport（OIDC adapter・Session Cookie・`Authorization`の解決）はserverの`server/src/auth`にある。

操作Contextの`activeRole`は、MCP・Runtime向けAPIのrequest header `X-Compass-Active-Role`で受け付ける（serverの`resolveActiveRole`）。headerがあれば、serverはrequestごとに`forActiveRole`で認可をそのRoleに固定したserviceを使う。Project・WorkはAccessの`ProjectAuthorizationService`・Workの`TaskCoordinationService`が`principalId + projectId + activeRole`のProject Grantを検査する。Directionの操作・参照と専門Role Contextは`RoleScopeAuthorizationService`が`principalId + workspaceId + activeRole`のWorkspace Grantを検査し、Project Grantから継承しない。MCPのDirection参照・`list_projects`は、remote modeに加えtrusted-localでもactiveRole指定時はそのRoleのGrantを要求する（headerなしのtrusted-localは互換としてGrantを問わない）。Principalなしでの指定はProject scopeのtool（管理操作の`update_project`を含む）とWorkspace scopeのDirection tool（Intent管理を含む）で`UNAUTHENTICATED`。trusted-localの`create_project`はProject作成前の操作でGrantの対象外のため、activeRoleの指定に関係なく実行できる。他Roleのtool・Grantの無いactiveRoleは`FORBIDDEN`。Accessが拒否する場合のうち、activeRoleと異なるRoleのtool、Project参照・管理操作でactiveRoleのGrantが無い場合は応答の`error.activeRole`にactiveRoleを返す（MCP・Runtime向けAPIとも`ForbiddenError`のdetailsを`error`へ展開する）。activeRoleと同じRoleのtoolでGrantが無い場合（`requiredRole`のみ）と、WorkのTask操作の拒否（`CoordinationError`）には含めない。未知の値は400。職務分離（Strategist等のGrantを持つPrincipalへの管理操作の拒否）は緩めない。headerなしは互換として操作ごとに必要Roleを検査し、拒否はRalph移行後に別途判断する。Runtime Credentialはheaderに関係なくscopeで認可する。`command_receipt.active_role`（nullable。既存行はNULL）に実行時のactiveRoleを保存し、同じ`principal_id + tool_name + request_id`を別のactiveRole（headerなしを含む）で再送すると`IDEMPOTENCY_CONFLICT`にする。自己レビュー・自己受入の禁止はPrincipal単位でWorkが強制し、Role切替では回避できない。Human向けWeb APIはMembershipで認可し、headerを読まない。

Accessは`project`・`workspace`のtableを直接読まない。archive判定・Projectの存在・owner不在Projectの補完に使うProject一覧は`ProjectStateReader` port、Workspaceのarchive判定・Workspace一覧・所属Project一覧は`WorkspaceStateReader` portで読み、Membership・Grant・Credentialの書込と同じtransactionで検査する。Workspace・Project作成時の初期owner Membershipは、OrganizationのWorkspace・Project作成（`SQLiteWorkspaceRepository`・`SQLiteProjectRepository`）のtransactionの中で、serverが`OwnerMembershipWriters`として渡したAccessの`writeWorkspaceOwnerMembership`・`writeProjectOwnerMembership`が書く。いずれもserverが`contextAdapters.ts`で配線する。AccessがOrganizationから使うのは公開indexのuse case（`GetProjectUseCase`・`ListProjectsUseCase`・`GetWorkspaceUseCase`・`ListWorkspacesUseCase`・`CreateWorkspaceProjectUseCase`。所属Project一覧の`ListWorkspaceProjectsUseCase`はserverが`HumanWorkspaceAuthorizedUseCase`で包む）・型（`ProjectDetail`・`ProjectStatus`・`Workspace`・`WorkspaceStatus`）・`ProjectArchivedError`・`WorkspaceArchivedError`だけで、AccessはDirection・Workに依存せず、OrganizationはAccessに依存しない。

## 現在のRuntime API

`fetch_runtime_events` / `ack_runtime_event`は現在利用可能。eventの取得・ackにはconsumer単位のcursorと配送状態がある。`list_changes`はExecutionの変更を取得し、`record_execution_evidence`はサーバーが現在状態から導出した結果とEvidence参照をDirectionへ還流する。

これらは現在の接続契約である。Orchestratorはeventではなく`get_workspace_orchestration_state`の現在状態で起動を判断し、Activity cursor・event cursorをworkflow checkpointにしない。Project基準の`get_orchestration_state`は除いた。Workspace単位の`get_workspace_orchestration_state`（Workspace Runtime Credentialのscope `runtime:state:read`だけ。Project Credential・trusted-localのAgent名は不可）は、Workspace・activeなProject・Active Intent・Outcome（Target別の`projectStatus`・Work件数・還流状態、全Targetの`evaluability`、最新EvaluationのProject別評価cursorと判断の有無）・Research Requestを同じ方針（ID・状態・件数だけ、読取専用、cursor非依存）で返す。archivedのWorkspaceは状態だけを返し、archivedのProjectは`projects`から除いてTargetとしてだけ示す。dispatch規則`planWorkspaceDispatches`（S08-02）はこの応答を入力にし、Orchestratorの周回がWorkspace Runtime Credentialで読む（S08-03）。既存Runtime APIをActivityとして流用しない。

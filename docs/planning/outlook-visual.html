COMPASS / OUTLOOK / 2026-11

自分の道具としては、十分に続ける価値がある。ただし、核はまだ仮説のまま

Compass は、作業管理（Wacha と Ralph）から始まり、方向づけと評価へ手を伸ばしてきました。作業管理の部分は、実際の開発で動いています。伸ばした先の「目標から評価まで」は実装がありますが、実際の Agent で1周したことがありません。将来性は、この1周を本物の目標で回せるかで決まります。

これは事実の整理ではなく、コードと公開情報を読んだうえでの私の見立てです。市場の今後は分かりません。

ここまでの歩み

1周のうち、どこまで確かめられているか

見立ての理由

続ける価値がある理由

  • 実装の並行化は、大手が埋めていく領域です。「何を作るか」と「作ったものが効いたか」は、まだ誰も解けていません。Compass はそこを設計の中心に置いています。
  • 実行の部分には、本物の運用の知見があります。障害史の38件は、動かした人しか持てない資産です。
  • 自分の道具なら、他の人に選ばれる必要がありません。自分の開発が進めば、それで成り立ちます。実際に、Compass 自身の開発で成果が出ています。

厳しい点

  • 核の仮説は、誰にも証明されていません。Agent が成果を証拠で評価して方向を決め直す、という部分です。評価に使う計測値の取り込みは未接続です。
  • 範囲が広すぎます。画面・認証・配置・相談・履歴を同時に作り込む間、核の検証が後回しになっています。
  • 実行の道具を2つ持っています。使っているのは agent-foundation 版で、製品の Ralph は使われていません。
  • 費用の上限と停止がありません。自分の道具でも、払うのは自分です。

自分の道具だと変わること

  • 導入の軽さ、対応する Agent の多さ、複数人での利用は、急がなくてよくなります。
  • 大手との競合は問題になりません。実行の部分は、良いものが出たら乗り換えれば済みます。
  • 安全性は変わらず必要です。Agent は自分のホストで、自分の権限を持って動きます。

分かれ目

本物のプロダクトと、数字で測れる本物の目標で、1周を回せるか。

たとえば「ある機能の利用率を上げる」と目標を置きます。Agent が Outcome を決めて実装し、公開した後の数字で評価し、次の手を変えます。これが1回成り立てば、他の事例にない実証になります。成り立たなければ、どこで崩れるかが分かり、それが次の設計の根拠になります。

Compass 自身の開発を題材にすると、目標が「機能を作ること」になりやすく、評価が受入と同じになります。利用者や数字のある別のプロダクトのほうが、評価の部分を試せます。

自分の道具としての進め方

先にやること

  1. 測れる目標を1つ選ぶ数字が取れるプロダクトと、1〜2週間で動く目標にします。
  2. 実行は、今動いている Ralph をつなぐagent-foundation 版の接続先を Compass に向ける形が、最も早い見込みです。製品の Ralph への全面移植より先に試せます。
  3. 成果を戻す処理と、数字の取り込みを1本だけ通す汎用にせず、選んだ目標の1つの数字だけで構いません。
  4. 費用の上限と停止を入れる1周を任せて回す前に必要です。
  5. 規則と配置設定を保護するGitHub の設定だけで始められます。

これ以上、磨かなくてよいもの

  • 複数人のための機能（招待、権限の細かい区別、メール送信）
  • 画面の作り込みと、部品のカタログ
  • Workers と D1 への配置（手元で回せるうちは不要）
  • 製品の Ralph への全面的な移植（つなぐ方法で足りるなら後回し）
  • 文書の精密さ（1周回すと、どの契約が要るかが変わります）

作ったものを捨てる、という意味ではありません。1周が通るまで、ここに時間を足さないという意味です。

1周が通った後に考えること

  • 対話しながらの開発（InteractiveWorkSession）
  • 目標を Agent と一緒に練る場
  • 実行の道具を自前で持ち続けるか、他の基盤に任せるか
  • 他の人にも使ってもらうか。その場合は「評価と統制の層」に絞るのが筋です

「今動いている Ralph を Compass につなぐ」は、接続先を差し替える仕組み（backends/）があることからの見込みです。認証や役割の扱いが違うので、実際にどれだけの作業かは未確認です。

# Story分割・AC・検証依存の再発防止案

本書は再発防止の提案であり、依存制御や自動修復の実装済み仕様ではない。実装Taskを登録する際に、採用範囲と所有システムを確定する。

## 反映状況

2026-10-14、開発用Wachaの共通手順へ段階1を反映した。

- Skill: `decompose-story` v4、`implement-task` v8、`review-task` v7、`accept-task` v2。
- Knowledge: `tips/story-splitting.md`、`tips/task-writing.md`、`tips/acceptance.md`。採用理由はWachaの `knowledge/CHANGELOG.md` に記録した。
- 受入境界、対象revisionでのGiven成立確認、差し戻し時の再評価、要件を保持した計画修正、停止原因の分類、有効なManager証拠の再利用を手順として追加した。
- 関連テスト12件・型チェック・差分チェックを通過し、稼働中MCPから更新済みSkillとKnowledgeを取得できることを確認した。

段階1の手順反映と配信確認は完了したが、今回と同型の計画をAgentが自律的に修正する効果は未検証。サーバーによるTask依存制御・構造化された停止分類・自動再開、および閉ループの統合検証は未実装・未実施。Ralphは起動していない。

## 今回の解消方針

Story 09のTask 02は自身のmerge SHAで成立するShell・Workspace切替・公開済み操作の表示同期を受け入れる。既存WorkspaceへのProject追加を使う複数Projectのブラウザ検証は、追加API/UIを実装するTask 03に割り当てる。Task 03の受入ではProjectとWorkspaceのarchiveの責務・認可を含めて検証する。

- Shell Task: `c10908b9-e8e2-4d1d-891f-e734eb34fa67`
- Workspace管理Task: `27e12ac0-6faf-4046-8c8c-b178ec2e0662`
- Story: `aad2c1ec-80ee-4ae8-b5b7-e463e6805451`

要件を取り除くのではなく、実行可能な検証位置へ割り当てる。過去の差し戻しコメントは証跡として保持し、現在のTask本文を受入条件の正本とする。受入SHAを後続commitへ勝手に変更しない。

## 原因

1. StoryにShellとWorkspace管理が含まれ、各Taskが独立して受け入れられる境界を明示していなかった。
2. 差し戻しで複数Projectのブラウザ確認を追加した際、そのGivenを作る公開入口が当該commitにあるか確認しなかった。
3. 後続Taskでarchiveの業務契約も変わるため、後続commitを先行Taskの検証対象にすると別の要件を混ぜてしまう。
4. Task番号・sortOrder・本文の前提には、実行を止める依存制御がない。先行Taskが未受入でも後続実装が進みうる。
5. 計画不整合を環境blockedとして扱い、再開しても同じ条件で停止する。取得済みの有効な証拠も繰り返し検証することになる。

## StoryとTaskの分割基準

StoryはHumanやAgentが達成する一つの成果を単位にし、Taskはその成果へ進む、検証可能な増分とする。固定のTask件数やレイヤ数で決めない。

- Storyを分ける例: 「既存Workspaceを選んで現在位置を把握できる」と「Workspaceを管理しProjectを追加・停止できる」。それぞれの公開入口・認可・UI・検証までを閉じる。
- 同じStoryに置く場合: Taskごとの受入境界を明記し、Story全体の統合条件には所有するTaskを一つ割り当てる。
- 共通基盤Task: 現在の画面に反映された観測可能な結果で受け入れる。未接続の将来画面の完成を要求しない。
- Taskを分けるためにUIだけ先行させる場合: 利用できる操作と中間状態を明示する。自身のACを満たすために後続Taskが必要なら、順序変更・縦切りへの統合・ACの割当変更を行う。
- 管理操作で重要な認可や業務規則を、単なる表示TaskのACに埋め込まない。操作を提供するTaskで状態遷移と画面への反映を合わせて確認する。

## 起票・差し戻し時の確認

Managerは新規ACと変更されたACについて、次の表を埋めてから公開する。Reviewerも差し戻し条件の追加前に確認する。

| 項目 | 判定する内容 |
| --- | --- |
| 所有者 | このACを完了させるTask IDは一つか |
| Givenの作り方 | 必要なデータ・Role・状態を、どの公開操作または承認済みfixtureで用意するか |
| 利用可能時点 | その入口は先行Taskで成立するか、同じTaskが提供するか |
| 観測方法 | 実ブラウザ・API・Domainテストなど、どの観測が必要か |
| 対象revision | Taskのmerge SHAで完結するか、統合確認用Taskのrevisionか |
| 依存 | 必要なTask IDと、実装・受入のどちらを待つか |
| 制約 | 権限・sandbox・一時データ・接続先・終了処理が実行可能か |

Givenに後続機能が必要なら起票を修正する。並び順の調整だけで済ませない。差し戻しは元の要件を満たす修正に限定し、新しい統合条件を追加する場合は所有Taskと依存を同時に決める。

## Agentが自力で解消する範囲

Managerは停止時に、製品不具合・検証環境・未成立の依存・ACの割当不整合・人の判断が必要な要件を分ける。Ralphは判定結果と再開条件を扱い、業務判断はManagerへ委譲する。

Managerが自律的に行う候補:

- 同じユーザー要件を保持したACの重複除去、検証位置の変更、Taskへの割当と前提の明示。
- 後続Taskへ移す際の条件保存と、移動先が未完了であり検証可能なことの確認。
- 計画を修正後、現在のACを照合した再受入。条件を満たしている証拠だけを利用する。
- 同じ状態での再試行を止め、依存が成立したときだけ再選択する。

人の判断が必要な候補:

- ユーザーの成果・制約・認可・業務規則を変更する。
- 必須条件の削除、未検証を成功扱いにする変更、証拠のない受入。
- 受入済みTaskへの義務の追加。必要なら追跡できる新しいTaskを起票する。

検証位置の変更を製品不具合の回避に使わない。AC修正前後と割当先を記録し、要件が失われていないことを確認する。

## 証拠の再利用

既存のManager証拠は対象Task・commit SHA・検証内容・データ・結果が一致し、ソース変更がなく、現在のACを満たす場合に利用する。Worker/Reviewerの承認だけで置き換えず、画像条件は保存画像を確認する。

ACの割当だけを直した場合は、残る条件に有効な証拠を照合し、不足だけを検証する。前回の`blocked`を`accept`へ機械的に書き換えない。現在のTask・Claim・PR状態を確認し、正規のMCPで新しい判断を記録する。

## 段階的な実装案

| 段階 | 所有・変更先 | 内容 | 完了条件 |
| --- | --- | --- | --- |
| 1 | 共通Skill/Knowledge | `decompose-story`・Story分割・Task記述・受入に、Givenの成立確認と差し戻し時の再評価を追加 | 今回と同型の計画を事前に検出し、ACを失わず実行可能な単位へ直せる |
| 2 | Workの計画・認可・選択 | Task IDによる依存と必要な到達状態を構造化。Project不一致・循環・存在しない依存を拒否し、Claim可能性の判定にも利用 | sortOrderを変えても未成立依存のTaskを取得できず、依存成立後はHumanなしで候補に戻る |
| 3 | Manager / Ralphの停止・再開 | 停止原因と再開条件を構造化。計画不整合はManagerへ返し、環境停止や要件確認と区別する | 同じ原因で無条件再試行せず、許可された計画修正・依存成立で再開できる |
| 4 | 統合検証 | 二つのTask・別merge SHA・後続APIを使うAC・差し戻し追加・有効証拠を含む閉ループ検証 | 起票修正→Task受入→後続の統合確認まで、状態と証拠を保持して完了する |

段階2以降はWorkが業務規則を所有し、Web APIとMCPが同じapplicationへ委譲する。Agent Foundation/RalphへProject固有の業務規則を埋め込まない。開発用WachaとCompassの責務・実装範囲は、実装Taskで別々に指定する。

## 評価する結果

- 計画不整合でのHuman介入回数と、同じ停止原因の再試行回数。
- ACの割当が失われた件数、未検証のまま受入された件数。
- 後続APIが必要なGivenを起票・差し戻し時に検出できた割合。
- 証拠を保ったまま再開できた割合と、同じ検証を繰り返した回数。

介入回数を減らすために受入基準を緩めず、計画の実行可能性と判断の回復性を改善する。

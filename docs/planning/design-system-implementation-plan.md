## 視覚方向

- 白と薄い青灰色を主体とし、青藍を現在地・主要操作・重要な方向情報に使う。ベージュ系の紙面表現を残さない。
- サンセリフとコンパクトな操作部品を使い、情報の優先順位・状態・次の行動を読み取りやすくする。
- 太い囲みや大きな余白を全要素へ一律に使わず、面・罫線・文字の強弱・配置で整理する。
- 状態色はブランド色と分ける。色だけで状態を伝えない。同じsize契約は共有し、navや通常リンク等の意味は保持する。
- ブラウザでプロトタイプと製品の対応画面を比較する。完全一致は要求せず、採用した方向と業務要件による差を説明する。

## カタログの選定と構成

- CompassはStorybookのReact/Vite構成を第一候補とする。導入時に実際のReact/Vite/TypeScript/Nodeとの互換性・保守負担を確認する。互換性等の具体的な理由があればLadle等の代替を比較し、Projectへ選定理由を記録する。新しいツールという理由だけで変更しない。
- 既存のButton/LinkButton、入力・Field・ViewSwitch、実際に共有している組合せ部品を再利用する。カタログ用の部品やSCSSを別実装しない。
- Foundations（色・文字・余白・size）、Components（API/用途/状態）、Patterns（操作列・フォーム等の組合せ）を、現在ある利用から整備する。
- カタログは製品のstyle入口・Provider/Router等を必要範囲で共有する。秘密情報、個人のログイン、実運用DBへの書込みを必要としない。
- catalogのdev/build/検証コマンドをpackage scriptへ接続する。部品の状態例は対応する部品の近くに置き、既存Feature境界・UI構造検査と両立させる。
- Agent向けmanifest/MCP等は採用版の対応・成熟度を確認し、必要なら使う。初期導入に必須としない。外部サービス契約・必須CI・有料画像比較は要求しない。

## 実装の増分

1. 既存の実部品・SCSSから起動/buildできるカタログを作る。この段階は現在の製品表示と一致すればよく、後続の新配色・全画面適用をACへ入れない。
2. 視覚方向をトークンと基本部品へ反映し、製品とカタログへ同時に適用する。用途/variant/size/状態/キーボード操作と比較画面で受け入れる。
3. Workspace/Projectの主要画面へ情報密度・配置・組合せを適用する。古い見た目が残る残存箇所を修正し、業務機能・認可・実データを維持する。
4. カタログと製品画面の統合検証、比較画像、現行ガイド、Worker/Reviewer/Managerの運用を整える。

UI構造整理StoryのAccepted成果を前提に再利用し、同じ共通部品を再実装しない。相談機能等の未実装の新機能をGivenに要求しない。新しい画面が並行して追加される場合は、取り込んだSHAの現在の画面範囲を明示して連携する。

## 検証と配信

- 状態例の描画・操作とカタログbuild、関連テスト・typecheck・lint・check:ui・製品buildを確認する。
- 実画面のDesktop/狭い画面、通常/空/権限差/失敗/disabled/pending等の関係する状態をブラウザと画像で確認する。カタログだけで画面適用済みとしない。
- 51800番の配信は製品buildの生成物を使う。確認時にHTMLが参照するassetと検証対象のbuild/SHAを照合し、古いassetの画面で受け入れない。
- ユーザー使用中DBではなく専用previewで検証する。必要なデータは既存公開操作または許可済み準備手順で作り、表示状態の準備と業務操作の検証を区別する。

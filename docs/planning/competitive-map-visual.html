COMPASS / SIMILAR WORK / 2026-11

似た取り組みと比べた、Compass の位置

Agent に開発を任せる仕組みは、多くの人が作っています。ほとんどは「実装をどう並行して回すか」を扱います。目標の管理まで扱うものは少なく、成果の評価まで扱うものは、調べた範囲では Compass だけでした。一方で、費用の上限・実行環境の隔離・実際の運用実績では、Compass が遅れています。

2026年11月時点の公開情報による比較です。各製品の記述は、公式ページ・論文・紹介記事の読み取りで、実際に動かして確かめたものではありません。図の位置と、表の「あり・一部・なし」は私の判断です。

組織を再現するPaperclipAgent の「会社」を運営する基盤。目標・組織図・予算・承認を持つ。最も近い事例

どんなものか

自分で動かす公開ソフトです（MIT）。組織の目標に仕事をひも付け、Agent に上司・肩書・担当を与えます。仕事の割当て・返信・定時の合図（heartbeat）で Agent が起きます。会社・Agent・Project ごとの予算があり、上限で止まります。Human は目標と予算を決め、採用の承認、一時停止、担当替えを行います。Claude Code・Codex・Cursor など多くの Agent を接続できます。

Compass との違い

目標はありますが、成果を証拠で判定する仕組みは公式の説明にありません。レビューと受入は、設定した承認の段階で行います。Compass のような、主体ごとの自己レビューの禁止や、PR の事実の照合は説明されていません。実行環境の隔離も説明がありません。

学べる点

予算と一時停止を最初から持っていること。Agent を起こす約束事が単純で、接続できる Agent が多いこと。1つのコマンドで始められる導入の軽さ。

出典：paperclip.ing/llms.txt

チームを再現するGas Town（＋ Beads）20〜30 の Claude Code を並行で動かす。7つの役割と、Git に保存する作業管理

どんなものか

Steve Yegge が公開した仕組みです。窓口の Mayor、作業する Polecat、merge の順番を管理する Refinery、作業者を見張る Witness などの役割があります。作業と Agent の状態は、Git に保存する作業管理（Beads）に置きます。Agent が途中で落ちても、次の実行が続きから再開します。

Compass との違い

目標や成果の評価はありません。扱うのは、1つのコードベースでの実装の並行化です。状態を Git に置くので Server が要りません。その代わり、認可や Human の画面はありません。紹介記事は、費用が1時間に約100ドルかかった例や、同じ不具合を複数の Agent が直す混乱を報告しています。

学べる点

merge の順番を専任の役割が管理すること。作業の各段に受入の条件を持たせ、落ちても続きから再開できること。費用の上限なしで並行数を増やすと何が起きるかの実例。

出典：Cloud Native Now、Software Engineering Daily

チームを再現するAgynmanager・researcher・engineer・reviewer の4役で、GitHub の PR を通して開発する

どんなものか

論文と公開の基盤です。manager が次に動かす Agent を決め、researcher が原因を調べて仕様を書き、engineer が実装し、reviewer が PR に指摘を書いて承認します。Agent ごとに GitHub のアカウントと、隔離された実行環境を持ちます。完了は、Agent の申告ではなく reviewer の承認で決まります。SWE-bench の500問で 72.2% を解いたと報告しています。

Compass との違い

役割の分け方と「完了は自己申告で決めない」考え方は Compass と同じです。違いは、目標・評価・Human の関与を扱わないことです。状態の正本は GitHub にあります。

学べる点

Agent ごとに実行環境を隔離し、GitHub のアカウントも分けていること。Compass は GitHub の同じアカウントを共有してよい設計で、ここが弱点です。

出典：arXiv 2602.01465

チケットで動かすOpenAI Symphony課題管理をそのまま指令の入口にする。仕様書と参考実装として公開

どんなものか

課題管理（issue・task・milestone）の項目ごとに Agent を割り当て、終わるまで動かし続けます。止まった Agent は再起動します。Agent が計画を立てて新しい課題を作ることもでき、Human がそれを確認してから割り当てます。完成した仕事は Human が確認し、差し戻せます。製品ではなく、各社が自分用に作るための仕様書と参考実装です。

Compass との違い

役割・目標・評価は定めていません。既存の課題管理を使うので、新しい作業管理を持ち込みません。Compass は自前の作業管理を持つので、統制は強くできますが、既存の道具とは別になります。

出典：InfoQ

商用の自律 AgentDevinクラウドで動く自律 Agent。大きな仕事を分けて、複数の Devin に任せられる

どんなものか

Cognition の商用製品です。1つの Devin が大きな仕事を分け、それぞれ隔離された VM で動く Devin に任せます。組織で共有する手順（Playbooks）と知識（Knowledge）を持ちます。2026年には、自社の設備で動かす形や、企業向けの費用と統制の仕組みを発表しています。

Compass との違い

扱うのは実装の委任です。成果は PR として Human に返ります。目標や評価はありません。Agent は Devin だけです。

学べる点

実行環境を VM で隔離していること。手順と知識を組織で共有する仕組みは、Compass の Skill・Knowledge と同じ発想で、運用実績があります。

出典：Cognition のブログ。統制の詳細は二次情報で、未確認です。

商用の管理基盤GitHub Agent HQ複数社の Agent に仕事を割り当て、権限と監査を GitHub で管理する

どんなものか

GitHub の上で、Copilot や他社の Agent に仕事を割り当てる「管制」の画面です。同じ仕事を複数の Agent に任せて比べることもできます。管理者は、使える Agent・モデル・アクセス範囲を決め、監査の記録を取れます。Agent が作ったコードにどの検査を走らせるかも制御できます。

Compass との違い

役割・目標・評価はありません。統制は、ブランチの保護や検査など、GitHub の既存の仕組みで行います。Compass が弱い「GitHub 側での強制」を最初から持っています。

学べる点

Agent の統制を、Agent の外にある基盤（ブランチ保護・必須の検査・監査の記録）で行うこと。Compass は Git の操作を Agent に任せているので、この層を使えていません。

出典：GitHub のブログ、TechTarget。2025年末の記事で、現在の機能は未確認です。

並行実行の作業台Vibe Kanban・Conductor・Claude SquadHuman が複数の Agent を並べて動かし、差分を見て merge する道具

どんなものか

仕事ごとに作業フォルダ（worktree）を分け、複数の Agent を同時に動かします。Vibe Kanban はかんばんの画面、Conductor は Mac のアプリ、Claude Squad は端末の中で使います。Human が仕事を渡し、差分を確認して merge します。

Compass との違い

Human が常に操作します。役割・目標・評価はありません。Compass で計画中の「対話しながらの開発」に近い領域です。

学べる点

Human が Agent と組んで進めるときの画面の作り（仕事の一覧、差分、状態）。対話しながらの開発を作るときの参考になります。

出典：crystl.dev の比較記事。販売側の記事を含みます。

仕様駆動の手法Spec Kit・Kiro・BMAD仕様 → 計画 → 作業 → 実装 の順に文書を作らせる進め方

どんなものか

Spec Kit（GitHub）は、仕様・計画・作業の文書を順に作るための雛形と手順です。Kiro（AWS）は同じ流れを組み込んだ開発環境です。BMAD は、分析・製品・設計・開発・検査などの役割を Agent に演じさせる進め方です。

Compass との違い

扱うのは「何を作るか」を文書にする部分で、成果物は Repository の中の文書です。実行の管理・認可・評価は持ちません。Compass の Manager が Story と Task に分ける段階に当たります。

学べる点

仕様と計画を、実装の前に Human が確認できる文書にすること。Compass は目標と Outcome を Human と練る場が弱いので、この流れを取り込めます。

出典：developertoolkit.ai、codemyspec.com

比べて分かった、Compass の強みと改善点

良いところ

成果の評価まで扱うのは、調べた範囲で Compass だけ他は「仕事が終わったか」までです。Compass は、先に決めた成功条件を証拠で判定し、次の方向を決め直すところまで設計しています。
受入と達成を分けているTask が受入されても、目標に近づいたとは扱いません。Agent の自己申告で進捗が良く見える問題を、構造で防いでいます。
決まりを Server が強制する自己レビューの禁止、作業権の排他、PR の事実の照合を、Agent の善意ではなく Server が行います。多くの事例は、手順や指示文に頼っています。
Agent から Human への相談が仕組みになっている会話・結論・待っていた仕事の再開まで扱います。他の事例の Human の関与は、割当てと最終確認が中心です。
戦略と実行で役割と範囲を分けているWorkspace で方向を決め、Project で実行します。1つの成果を複数の Project で分担できるのは、他にあまり見られません。

改善するところ

費用の上限と一時停止がないPaperclip は最初から予算と停止を持ちます。Gas Town は、上限なしで並行させると費用と混乱が膨らむ例を示しています。
実行環境を隔離していないDevin は VM、Agyn は Agent ごとの環境で隔離します。Compass の製品側は、権限確認を省いた Agent がホストで動く設定例です。
統制が GitHub 側に届いていないAgyn は Agent ごとにアカウントを分け、GitHub Agent HQ はブランチ保護と検査で縛ります。Compass は同じアカウントの共有を許し、merge の後に照合します。
動いた実績がない他の事例は、粗くても実際に回っています。Compass は目標から評価までを実 Agent で通していません。設計の優位は、1周回して初めて確かめられます。
導入と接続が重いPaperclip は1つのコマンドで始まり、10種類ほどの Agent をつなげます。Compass は Server・Orchestrator・Ralph の設定と認証の発行が要り、対応は Claude Code と Codex です。
merge の衝突を扱う役割がないGas Town は merge の順番を専任で管理します。Compass の製品側には、並行する変更の取り込みを調整する仕組みがありません。

進む方向としては、実装の並行化で競うより、「目標から評価まで」と「Server による統制」を伸ばすのが筋です。実行の部分は、隔離・予算・merge の管理など、他の事例で確かめられたやり方を取り入れられます。

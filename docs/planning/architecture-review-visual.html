COMPASS / ARCHITECTURE REVIEW / 2026-11

Compass の全体像と、Agent だけで回すときの弱点

Compass は、Human が与えた目標から、専門の役割を持つ Agent が計画・実装・検証・評価を進めるための基盤です。前半で仕組みを図にし、後半で「Human を挟まずに回す」前提での懸念を、現状と改善後の図で比べます。

改善後の図は提案で、確定した設計ではありません。根拠は 2026-11-12 時点の feat/fit2cloudflare ブランチのコードと文書です。

一目で見る：誰が、何を、どの順で進めるか

総評：骨格は良いが、Agent を「間違えるが誠実な作業者」としてしか見ていない

筋が良いところ

状態と認可を Server に集め、Agent の起動を外に出した分離は正しい判断です。起動判断を現在状態だけで行うので、途中で落ちてもやり直せます。成功条件を先に固定し、受入と達成を分けた点も、Agent の自己申告を防ぐ土台になります。

根本の弱点

守っているのは手順の整合（誰が Claim したか、自己レビューでないか）です。Agent が誤誘導されたり乗っ取られたりした場合に、被害を閉じ込める仕組みがありません。Agent は自分の規則を書き換えられ、書込み権限とホストの shell を同時に持てます。

進め方の弱点

契約と文書は非常に精密ですが、実 Agent で目標から評価まで通した実績がありません。ループには人手が要る切れ目も残っています。1周も回していない仕組みに、精密さを先に積んでいます。

現状と改善後の比較

重大

Agent が、自分を縛る規則を書き換えて配信できる

役割の定義（roles/）・手順（skills/）・共通の決まり（policies/）は、Worker が変更する同じ Repository にあります。Worker が PR に含め、Reviewer（Agent）が merge すれば、Server はその内容を次の指示として配ります。Workers 配置では main への push がそのまま本番の配置になります。変更できるパスを制限する仕組みは、製品側には見つかりませんでした。

重大

Agent が、書込み権限とホストの shell を同時に持つ

製品の Ralph の設定例は、Claude Code の権限確認を省く指定（dangerouslySkipPermissions: true）です。PR の作成や merge は Agent が gh で行う手順なので、GitHub の書込み権限が Agent の実行環境に要ります。Task の本文や Web の内容に紛れた指示で Agent が誤誘導されると、その権限と通信手段がそのまま使われます。Server の照合は merge の後です。

高

止める入口と、費用の上限がない

目標を登録した後は、Outcome の決定から merge、Workers 配置なら本番への反映まで、Human の確認点がありません。Server には Workspace を一時停止する操作も、費用の上限もありません。Orchestrator の再試行上限は起動単位で、状態が進むたびに新しい起動が生まれます。止めるには、プロセスを落とすか Workspace を archive するしかありません。

高

ループが途中で切れている

製品の Compass では、Reviewer の後の受入を起動する仕組みがありません。Orchestrator も製品の Ralph の自動実行も、Manager の受入を起動しません。開発で使っている agent-foundation 版の Ralph は受入まで起動しているので、これは製品側へまだ取り込まれていない差分です。受入した成果を Outcome へ戻す処理（Evidence の還流）は、どちらにもありません。そのため、製品では Evaluator まで自動では届きません。

進める順番

  1. 規則と配置設定を保護パスにし、main への直接 push を禁じる。設定だけで済み、最も効果が大きい。
  2. Git の書込みをホスト側の Ralph に集め、Agent を sandbox に入れる。Ralph の一本化と同じ作業になる。
  3. Workspace の一時停止と費用の上限を Server に入れる。
  4. 受入の起動を製品へ取り込み、還流を追加して、実 Agent で1つの目標を評価まで通す。
  5. その後に、対話しながらの開発（InteractiveWorkSession）へ進む。

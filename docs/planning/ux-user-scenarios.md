# UI・UX再設計：利用シナリオとページ構成案

## 位置づけ

主要ページの情報構成・名称・配置・導線は利用者と合意した現時点の設計基準とし、本資料と試作を実装の起点とする。利用時のフィードバックに応じて改善する。業務契約・状態別表示・集計等の未確定事項は各節に明示し、主要画面への合意を全要件の確定として扱わない。基本の情報構造とAgent Roleの責務は維持し、Human認可はADR 0003に従う。試作はサンプルによる画面確認用であり、本体のコード・DB・実行設定・公開APIを実装済みとは扱わない。

## 設計の土台と利用者の要望

- Workspaceはビジネス全体を捉える戦略の境界、Projectは紐づくプロダクトの実行境界として使う。ProjectとRepositoryは同一視しない。
- Humanは複数Workspaceを行き来する。一つのWorkspaceを複数Humanで共有できるが、今回は人ごとの担当分担を前提にしない。
- ビジネス目標は当面AgentとHumanが相談して決める。プロダクト側の目標・進め方はAgentへ任せ、人が必要に応じて介入できる体験を望む。AgentのRole・Grant・認可境界を拡張する決定ではない。
- 大きな枠組みから詳細へ掘り下げる。概要は要点、判断材料・内部の仕事は詳細で確認する。
- 頻度と閲覧順序の仮説は「たまに戻り、到達点→変化・進捗→人の対応を確認する」。観察済みの利用行動ではない。
- 一度に一つずつ質問し、回答から掘り下げる。判断材料が揃った段階で構成案を示して確認する。質問を増やすこと自体を目的にしない。
- 会話の進捗率は設計論点を整理できた程度の目安として示す。増減を許し、開発完了率や検証済み割合と混同しない。

DirectionはWorkspaceのIntent・Outcome、実行管理はProjectのStory・Taskに置く。Agentで解消できる通常の障害と、Humanの判断が必要な対応待ちを分ける。Taskの受入、公開確認、Outcomeの達成を別の状態として表示する。利用者が読むActivityと調査用のOperational Logも分離する。

Ralphの細かな設定、ローカルファイル構成、復旧・清掃・ログ管理等を一括で移植することは今回のUI設計の対象に含めない。ただし、Claim・成果物・実行状況等の接続に必要な情報と責任境界は確認する。

次はTask詳細のClaim・レビュー・受入・差戻し・成果物の表示とHuman操作を優先して確認し、続いてStory／Taskの手動起票・編集を詰める。GitHub連携の不足は本体側の実装課題とUI側の表示課題に分ける。実装が必要な変更は、対応するStory・Taskに登録してから進める。

## 表示内容の合意・仮置き

### Workspace全体

入口では売上・DAU等のKPIを並べず、左にWorkspace名・Mission・Vision、右に独立した問題情報と対応待ち件数を表示する。問題が複数あれば代表1件と残りの件数を示す。問題の判定・影響度の整理には観測可能な根拠を使い、未確認を問題なしと扱わない。

Workspace概要ではビジネス目標全体を俯瞰し、要点から詳細へ移る。目標詳細では一つの目標のKPI推移・Agentの説明・仮説／施策の要約をまとめる案を試す。情報量が多ければ分ける。

Agentの説明は、確認できた変化、関連する施策、解釈・原因の仮説、次の打ち手の提案とする。因果関係を断定せず、根拠を辿れるようにする。ビジネス指標の取得・説明生成は実装済みとは扱わず、未計測・未接続・判断不能を区別する。

### 施策とProject

施策詳細で複数Projectの提供機能・開発状況をまとめて見たい。一方、Project概要は現在の状態を示し、Outcomeごとに「目的・関連Taskの進捗率・止まっている問題」を並べる。

Taskの完了はManagerが受入した状態で数え、レビュー・受入待ちは別に示す。対象は当該Outcomeに関係するTask。重み付け、取消Task、Task追加による分母の変動、Taskゼロ件の扱いは未決定。Task進捗率とOutcome達成度は別である。

問題一覧は人の判断待ちに限らず、依存待ちやAgent側で対処する障害も含む。理由・影響範囲・対処状況・次に進む条件を示す案とし、必要な相談・介入は詳細から行う。

### 人の対応とフィードバック

人向け一覧はWorkspace単位。全Workspace横断の対応一覧は作らず、入口から各Workspaceへ入る。回答しない場合の影響と期限から、今対応しないと困る順に見たい。評価方法は未決定。

対応詳細は、まず「今決めること・Agentの推奨と理由・期限と影響」の要約、その後に経緯・関連情報と回答の場を置く。即答できそうでも確認してから回答する。任意の成果物フィードバックは必須対応一覧に混ぜず、成果物の詳細に入口を設ける。

Workspace共通の対応として誰か一人が回答・判断すれば進む使い方を望む。ただし既存の認可・相談のrevisionや排他を省略する意味ではない。

### Agent管理と記録

仕事と作業者は分ける。Agent管理はWorkspace内の一覧へ集約する仮案。Principal、担当Role・Project、現在の作業、稼働／停止・エラー、Principal登録・Credential発行等を扱いたい。scopeは区別する。

想定運用は「一つのPrincipalは一つのRoleで複数Projectを担当し、別Workspaceは担当しない」。これは利用想定であり、既存の複数Role Grantを禁止するschema変更の決定ではない。Principal登録とCredential発行は別の操作として整理する。稼働状態をGrant・Credential・Claimから推測しない。

WorkspaceのActivityには、AgentとHumanを同じチームの活動として含め、Workspace共通と配下の閲覧可能な全Projectの業務上の活動を時系列・検索で辿れるようにする。重要度だけを理由に活動を除外しない。コメントは対象詳細で読むものとしてActivityへ掲載せず、内部通信・Claimの定期更新・技術的エラーログも分離する。

Projectの提供済み成果は細かなリリース履歴として残す。後から要約できても原記録は保持する。変更内容から目標・Outcome、Task・PR、公開確認の根拠へ辿れるようにする。開発・検証完了と公開済みを区別し、公開が不明ならそう示す。デプロイ方式ごとの専用画面を増やさず、必要な連携設定はProjectの設定に収める案。公開の取得・判定方法は別途実現可能性を確認する。

## 代表的な導線案

- 成果と変化を見る：Workspace一覧 → Workspace概要 → 目標詳細 → 施策詳細 → 関連Project／成果物。
- 仕事を掘り下げる：Project概要 → 対象Outcomeの開発詳細 → Story／Task → PR・検証証跡。
- 問題を見る：Project概要の問題一覧 → 問題詳細 → 必要なら相談・介入。人の回答が必要なら同じ対応詳細へ辿る。
- 人が対応する：Workspace一覧の件数 → 該当Workspaceの人の対応一覧 → 要約・経緯・関連情報を持つ対応詳細 → 回答。Workspaceを越えて一括回答しない。
- 過去の成果を見る：Projectのリリース履歴 → 変更の詳細 → 目標・Outcome・Task・PR・公開の根拠。
- Agentを管理する：WorkspaceのAgent管理 → Principalの担当scope・状態・設定 → 必要な担当Projectや作業。

参照関係を辿っても元のWorkspace・Project・目標へ戻れるようにする。複数の入口から同じ詳細へ辿れるが、本文や会話を複製して別管理しない。

## ナビゲーションの利用方針

- モーダル共通の閉じる操作は右上の×アイコンとし、文字のボタンを置かない。44px以上の操作領域と読み上げ用の「閉じる」を持たせ、閉じた後は開いた操作へfocusを戻す。
- SPのメニュー入口はヘッダー内の名前アイコンの右に、ハンバーガーアイコンだけを置く。メニューパネルはボタンと同じ右側に表示し、閉じる操作は右上の×アイコンとし、Workspace選択と同じ行に置いて専用行を作らない。タップ領域とアクセシブルな名前を確保する。PCは左メニューを維持する。アクセシブルな名前と開閉状態を持たせ、ヘッダー下の独立したナビゲーションバーは置かない。メニュー内のWorkspace／Project切替と階層は維持する。

- WorkspaceのメニューはProject閲覧中も残す。そのメニューから同じWorkspace内の別Projectを選べるようにし、選択中のWorkspace・Projectを明示する。
- Projectを切り替えたら、切替先の概要を開く。元のProjectで開いていた詳細やタブを、そのまま別Projectへ持ち越さない。
- Workspaceを切り替えた場合も、切替先のWorkspace概要を開く。
- Project内の上部タブは置かず、選択中のProject名の下へ概要・開発詳細・リリース履歴・設定を一段下げて表示する。Workspaceの主メニューは維持し、Project名を選ぶと概要へ戻る。
- 本文は上端に配置し、短いProject画面が縦方向に中央寄せされて大きな上部余白が生じないようにする。
- Outcomeから掘り下げる流れに加え、Projectへ直接入る入口も維持する。Project単位の介入・対話的開発は実行機構側の検討事項として保持し、UIのページ構成の合意だけで実装済みとは扱わない。

## 利用端末と滞在時間の仮説

PCを主な利用環境として挙げたが、スマートフォンの利用時間のほうが長くなる可能性もある。スマートフォンも日常利用の中心になり得るものとして、短い状況確認を頻繁に行う場面と、グラフ・説明・関連情報をじっくり読む場面の両方を試す。実際の利用頻度・滞在時間は未観察。

- 両端末で、全Workspaceの入口から概要・詳細へ進み、人の対応を行える体験を設計する。スマートフォンを単なる閲覧用の縮小版にはしない。
- スマートフォンでもProjectの管理操作を扱いたい。具体的な項目・フォーム・認可は既存契約と照合して設計する。
- Agentの登録はスマートフォンで必要としないという要望に基づき、PC側の管理体験に置く。Agentの登録・Credential発行・実プロセスの起動は別であり、スマートフォンから起動することが技術的に不可能と確定したわけではない。
- 短時間の利用では概要から状況と次に見る対象を選べ、長時間の利用では同じ情報構造から詳細を読めるようにする。別の業務構造・会話・履歴を端末ごとに作らない。
- 固定ナビゲーションはProject間の切替入口を残す意図。スマートフォンでも常に大きなsidebarを表示することを意味しない。具体的な表示・開閉・戻り方は未決定。

## 好みの記録と統合

UIレビューで示された好みを、一般的な正しさや利用者検証済みの事実とは区別して記録する。各指摘を反映する都度、関連する既存の方針も置き換え、同じ条件で矛盾する記述を残さない。異なる条件の要望は一覧／詳細、PC／SPなどの適用範囲で整理する。現在の資料に旧案と変更経緯を併記せず、履歴はGit等で参照する。

次の画面・Projectでも使う好みはagent-foundationの`design-information-architecture/references/design-preferences.md`で管理する。製品固有の配置・ページ名・値は本資料に保持する。利用者への確認は、記録を一意に統合できず設計に影響する場合に限る。

## 文言とリンクの設計方針

入口の情報から見るべきWorkspaceを判断できそう、という利用者の評価を得た。実際の継続利用での有効性は引き続き検証する。

- Workspace概要へのリンクはWorkspace名に集約し、名前の横の矢印・重複する「概要を開く」は置かない。
- Human向けの表示名は「対応待ち」とする。範囲は、誰かが対応しないと進まない事項という合意を維持し、任意のフィードバックを混ぜない。
- 問題の有無は状態ラベルと実際の理由で伝える。用語の補足や画面の使い方を説明する文を常設する前に、表示名・配置・関係で意味が伝わるか確認する。
- Workspaceが何のビジネスかという説明や、停止の理由・判断材料など、対象の内容を理解する情報は残す。説明文を一律に消すルールにはしない。
- 試作品のサンプルデータ表示、欠損・未接続の状態、操作に必要な注意は、誤認や操作判断に必要な情報として扱う。

## Workspace一覧の情報配置

- 左側は概要。Workspace名を概要へのリンクとし、MissionとVisionを表示する。Visionは最大2行に制限して超過分を省略し、全文はWorkspace概要で確認できるようにする。
- 右側は状況。「問題」と「対応待ち」を同じ階層の独立した領域として並べる。問題数と対応待ち数は別の集合・意味であり、合算した状態ラベルや一体の通知にしない。同じ事象が両方に関係しても、関係を詳細で示す。
- 問題側は「問題あり／問題なし」を領域の見出しとして使い、別の「問題」という見出しを重ねない。問題があれば代表1件の説明、複数あれば「ほかx件」を表示し、問題一覧へ辿れる。代表を選ぶ基準は影響の大きさ。具体的な評価方法は未決定。
- 対応待ち側は人が対応しないと進まない事項の件数から、同じWorkspaceの対応一覧へ辿る。
- 進行を妨げる問題の有無・内容を示す。問題なしと未確認を区別し、取得に失敗した状態をゼロ件として扱わない。
- スマートフォンでも、概要の下に問題・対応待ちを横並びに置く案を試す。情報の階層はPCとそろえ、枠・間隔・区切りで別物と分かるか確認する。

## ビジネス目標・Intent・Outcomeの意味の整理

設計方針は、Mission／Visionを背景に、Intentへビジネスとして実現したい状態と成功条件を置き、Outcomeへその実現に貢献すると考える観測可能な変化を置くこと。Intentを解決策の仮説と同義にしない。管理の骨格はIntent → Outcome → ProjectのStory／Taskとし、ビジネス目標のためだけに上位の必須階層を追加しない。

Outcomeには、その変化を妨げるProblem Statement、調査の根拠、解決策の仮説を関連付ける案とする。課題と解決策を独立Entityにする範囲は未確定であり、必須の管理階層や承認工程を先に増やさない。「解決策が課題に効くか」と「課題の改善が事業成果に貢献するか」をそれぞれ検証する。課題の解決件数やTask進捗率からOutcome達成度を機械的に算出しない。

Intentは自由記述だけにせず、Agentが目的・成功条件・制約を読み取れるよう構造化する。項目案は実現したい状態、背景・理由、対象・範囲、成功条件、現状と根拠、評価時期、制約。成功条件には指標・目標・測定方法を関連付け、数値以外の確認可能な条件も扱う。必須項目と登録時の検査は未確定。未計測をゼロや達成として扱わず、解決策の確定を開始条件にしない。

KPIは結果・変化を測る指標であり、仕事そのものではない。目標詳細・施策詳細のラフは表示構造の案であり、構造化したIntentや新しいGoal／施策Entityが実装済みという意味ではない。

現行実装のIntentはHumanが実現したい状態（desiredState）、OutcomeはIntentへ近づくための観測可能な状態で、Outcome側にhypothesisと成功条件を持つ。Active IntentはWorkspaceに最大1件で、Outcomeを持つIntentのdesiredState等やOutcomeの成功条件には変更制限がある。複数目標の俯瞰、学習による見直し、提供後の継続評価との整合を実装前に確認する。UIの検討だけで現行の保存・更新契約を変更しない。

関連フォームの具体例は、Intentに表すビジネス目標、Outcome、課題と解決策の仮説、Story／Taskの関係が一貫するものとする。各欄が何を書く場所かを区別できる例とし、サンプルを保存済みの値や必須の事業指標と誤認させない。入力のヒントが操作後に失われないよう、必要に応じて補助例の提示方法も検討する。

## 目標の作成・編集とAgentへの接続

IntentはCompass UIから項目を直接入力して作成・編集できるようにする。UIにHumanから目標の相談を始める窓口やAIチャットを設けない。AIと相談して目標を具体化する場合は、Codex CLI・Web版・アプリ等の外部クライアントを使う。CompassからOpenAI APIを直接利用する構成は不要とする。この方針は目標作成の相談入口に関するもので、Agentから届く対応待ちの閲覧・返信を廃止する意味ではない。

外部MCPクライアントでHumanとAgentが相談し、権限のある主体がMCP経由で目標を登録・更新する使い方も正規の入口として設計する。UIとMCPは同じapplication層の入力規則・業務規則を利用し、同じWorkspaceのIntentを参照・編集する。MCPで登録した内容をUIで再入力する必要はなく、外部会話の全文保存も必須にしない。整理した項目と判断の根拠を保持し、操作主体は認証情報から記録する。Agentによる記録をHumanの直接操作として扱わない。

現行のIntent作成・更新MCPはtrusted-localに限られ、Workspace Direction Roleを持つAgentやactiveRole指定の操作には公開されていない。外部MCPからの正規登録には、対象Workspaceの権限・操作契約の追加が必要。接続設定だけで実現済みとは扱わない。

ビジネス目標（Intent）の直接入力フォームは「目標名・実現したい状態」「背景・対象・制約」「達成条件・目標日」に分け、入力欄を最初から表示する構成を採用する。Workspace概要の「目標を作成」と、目標詳細の「編集」から開く。必須条件は未確定で、試作では現行の必須項目である目標名・実現したい状態だけを必須としている。作成・保存ボタンは入力内容のプレビューを表示し、実データの登録・更新やAgent起動は行わない。新規画面は空欄、編集画面はサンプル値を表示する。

Intentの登録後は、Agentが調査の要否を判断し、必要な調査やOutcomeの具体化を始める。登録と着手を分けるHumanの開始操作を必須にしない。登録の完了とAgentの起動・稼働は区別し、Agent未起動・応答失敗を登録失敗や稼働中と誤表示しない。MCP側のRole／権限、Outcome作成後の編集制約との整合は未確定であり、本メモではコード・実行設定・配信Role文書を変更しない。

OutcomeはAgentによる具体化に加え、HumanがUIから直接登録し、権限のあるAgentが外部クライアントからMCP経由で登録できるようにする。両方を通常の入口として維持し、同じWorkspaceのIntentに結び付け、共通のapplication層で入力・業務規則を検査する。作成主体を記録し、作成経路によって別のOutcome管理や二重入力を生じさせない。現行にもWeb UIとstrategistのMCPによる作成経路があり、再設計でも維持する。新しい画面の登録入口とフォームはワイヤーフレームであり、閲覧用Outcome詳細やフォームの合意を製品の登録機能の完成と扱わない。

## Agentを中心にした探索・評価

評価計画は検討対象とするが、Success Metricsの独立した管理機能・専用入力は初期スコープに含めない。評価に必要な指標は評価計画の中で扱い、既存のOutcomeの成功条件とは別に必須の管理項目を増やさない。

初期スコープにインタビューの実施機能を含めず、認知的ウォークスルーを設計の評価方法として採用する。対象ユーザーの知識・目的・利用状況を定め、操作の必要性、操作箇所の発見、目的との対応、結果の理解を点検する。Agentが操作できた結果と、実ユーザーによる使いやすさ・価値の実証を区別する。

提供後は利用行動・事業指標等の定量データで効果を評価する。A/Bテストや差分の差分法は候補とし、全Outcomeで特定手法を必須にしない。A/Bテストは無作為割付や必要な標本数等、差分の差分法は適切な比較群・介入前後のデータ・介入が無ければ推移が平行であったという仮定等について、適用可能性を確認して選ぶ。単純な前後比較を因果効果の証明として扱わない。これらの計測・分析基盤は実装済みではない。

評価計画には、確かめる仮説、主要指標、悪化させてはいけない指標、取得データ、評価方法と前提、観測期間、判断・中止条件を持たせる案とする。評価結果には方法・根拠・限界を残し、データ不足は判断不能として次の計測・観測へつなぐ。判断不能を成功や自動的なHuman待ちへ変換しない。Researchを全ケースの必須ゲートにせず、根拠と不確実性に応じて調査・試作・小規模提供・評価を反復する。

## Projectの開発詳細・Task詳細のラフ

Projectの開発詳細は、初回表示で「すべてのOutcome」を選び、同じProject内の全Story・TaskとOutcome未設定の作業を横断して閲覧できるようにする。Outcomeを選ぶことを閲覧の前提にしない。Project概要の特定Outcomeの進捗から進む場合は、そのOutcomeに絞った表示へ直接移動する。別Projectの作業を認可なしに横断する意味ではない。情報構成と導線を現時点の設計基準として採用する。

表示は「Storyごと」と「Task一覧」を切り替える。Storyは10件ずつ表示し、初期状態では題名・Outcome・Task件数等の要点を表示する。Storyを1回開くと、受入条件の全文とTaskが同時に見えるようにし、受入条件だけをさらに開く入れ子の操作を置かない。SMART等で長くなる受入条件はStoryの開閉で表示量を調整し、展開後は省略せず読めるようにする。Task一覧はStoryやOutcomeをまたいで20件ずつ表示し、所属Story・Outcomeを要約して添える。Task一覧は試用として維持し、利用時の有用性に応じて削減を検討する。検索・状態の絞り込みは全ページ分を対象とし、該当するStory／Task数と現在ページの表示範囲を別に示す。Taskの状態、止まっている理由と「Agentが対処／対応待ち」を示す。仕事と作業者を主情報として混ぜず、Agentの一覧・管理は別画面に置く。Taskの状態が作業中でも、Agentプロセスが稼働中と推測しない。差戻しや相談待ちの理由を、Taskの状態と区別する。

進捗率は選択した範囲の受入済みTaskを分子とする。検索とTask状態で表示件数を絞っても進捗率の分母を変えず、表示件数を別に示す。表示量の検討基準として、開発用WachaのCompass Projectを読み取り、25 Story・122 Task、最大13 Task／Storyを確認した。同規模の架空データを試作に用意し、Wachaの実際の状態・本文は取り込まない。特定Outcomeの小さな例は2 Story・10 Taskで、受入済み6件、作業中1件、レビュー待ち1件、受入待ち1件、未着手1件。関連するProject・Outcome概要は対象範囲に応じたサンプル値を表示する。取消や重み付け・Taskゼロ件・分母の変動の正式な規則は未確定。

Task詳細は状態、Storyへの所属、実施内容、受入条件、止まっている／差戻しの理由、関連PRへの参照、関連Outcome・公開状況、コメント欄を置く。Humanの判断が必要な例は対応詳細へ進む。関連PRとコメントの検証報告は仮表示であり、実際の履歴照合規則や検証結果とは扱わない。コメントもプレビューのみで、登録・状態変更・Agent再起動は行わない。

## Activityのラフ

Workspace共通と配下の閲覧可能な全Projectについて、作成・着手・作業完了・レビュー・差戻し・受入・目標変更・調査・問題等の業務上の活動を、新しい順・日付ごとに表示する。Workspace概要は最近の重要な活動を数件に絞り、Activity一覧は全体を検索・絞り込みできる入口とする。Task詳細の活動履歴は同じ業務上の出来事をTaskに絞って表示する。コメントは各対象の詳細で読み、コメント追加イベントや本文の抜粋もActivityへ掲載しない。各記録は時刻、主体、対象Workspace／Project、種別、題名、要約を持ち、題名から詳細へ進む。技術的なエラーログや全操作の監査記録をこの一覧へそのまま並べない。一覧・詳細と関連情報の閲覧構成は、確認したワイヤーフレームを基準として採用する。

検索は題名・要約・本文・判断理由・主体の文字列を対象とし、対象と種別を併せて絞れる。対象の「すべての記録」はWorkspace共通と閲覧可能な所属Projectの記録を含み、「Workspace共通」はProjectに属さない目標・方針等の記録だけを示す。各Projectを選ぶと、そのProjectの記録に絞る。対象の名前だけで全件とWorkspace共通を区別できるようにする。条件に一致する件数と0件の表示、条件をまとめて解除する操作を用意する。種別の「成果・判断・調査・問題」は表示上の分類案で、現行Activityのtypeへの対応は未確定。検索やProject横断取得の実装済み機能を意味しない。

詳細では、何が起きたか、根拠・判断理由、関連する目標・Outcome・Project・対応事項等への参照を表示する。Humanの共有した方針とAgentの判断・観測を区別し、観測から未確認の原因を断定しない。レビュー完了やTask受入を公開済み・Outcome達成として扱わない。意味のある記録としてのActivityと、処理の再開位置や実行ログは分ける。

Workspace内の一覧へまとめてもProject／Workspaceの所有・認可を統合しない。実装では認可された記録だけを検索・集約・ページングする必要がある。試作は架空の記録5件を使う表示例で、実際のActivityや自律運転の実績には接続しない。件数増加時のページング、期間指定、詳細から戻った際の検索条件保持は未確定。

PC 1440px・スマートフォン390pxで表示、検索、対象と種別の複合絞り込み、0件、条件解除、記録詳細と関連する対応詳細への遷移を確認した。横方向のはみ出しとブラウザのコンソールエラーはない。認可・実データ保存や検索性能の受入とは区別する。

## Agent管理のラフ

Workspace内のAgentをPrincipalごとに並べ、Role、担当範囲、実行状況、確認時刻・情報不足の理由、現在の作業を表示する。一覧では作業中・待機中・エラー終了・不明の例を用意する。担当範囲はWorkspaceとProjectを区別する。一覧ではProject名1件と、複数ある場合の「ほかN件」を1行で表示する。長い名前は省略し、件数が増えても担当先の欄が縦に伸びないようにする。Workspace担当は「Workspace」と表示する。担当Project全件と各Projectへのリンクは詳細で確認する。この表示を当面の採用案とし、利用時の不便に応じて見直す。名前から詳細へ進み、関連する仕事・Projectを辿れる。一覧・詳細の情報構成と導線は、確認したワイヤーフレームを基準として採用する。最終的な製品UIや管理操作の受入とは区別する。

詳細では担当Role・範囲、実行状況、scope別のCredentialを分けて表示する。Credentialの有効性やGrant・Claimからプロセスの稼働を推測しない。実行状況の取得方法や、情報が古くなった場合の判定は未確定で、試作内の状態・作業・確認時刻・Credentialは全て架空のサンプルである。

PCにはAgent登録とCredential発行のフォームを用意する。Agent登録ではPrincipal・Role・担当範囲を指定し、Workspace RoleならWorkspace、Project Roleなら一つ以上のProjectを指定する。これは一つのPrincipalに一つのRoleを割り当てる利用想定の試作で、既存の複数Role Grantを禁止するschema変更ではない。Principalの登録・Grant付与とCredential発行は別の操作とし、登録によるtoken発行やAgent起動を暗黙に行わない。

Credential発行では対象scopeと有効期間を確認する。更新・取消は入口の仮表示であり、操作の最終構成は未確定。試作ではtokenの生成・表示・保存、認可の変更、Credentialの更新・取消、プロセス起動・停止を行わない。スマートフォンは一覧・詳細の確認を中心とし、登録やCredential操作の入口はPCに配置する。表示の制御をServerの認可の代わりにはしない。

PC 1440px・スマートフォン390pxで表示と横方向にはみ出さないことを確認した。複数Projectを担当するWorkerの登録内容、Project未選択時の案内、Workspace Role選択時の範囲表示、Credential発行内容のプレビュー、取消入口、スマートフォンの管理入口の非表示を確認し、コンソールエラーはない。実際の管理操作・認可・Agent稼働の検証とは区別する。

## 対応待ちのラフ

対応待ちの一覧・詳細は、確認したワイヤーフレームの情報構成と導線を採用する。Workspaceのメニューと概要の対応待ち件数から、同じWorkspaceの一覧へ進む。回答しない場合の影響と期限を並べ、題名から詳細へ移動する。試作は公開準備の停止と外部接続検証の停止という2件を影響・期限の判断材料付きで並べる。優先順位を算出する正式な規則は未確定。任意のフィードバックやAgentだけで解決できる通常作業は混ぜない。構成への合意と、製品の送信・認可・状態遷移の受入は区別する。

詳細の上部は今決めること、Agentの推奨と理由、期限、回答がない場合の影響を要約する。その後に関連する目標・Outcome・Projectへのリンク、HumanとAgentの経緯、回答欄を置く。選択肢だけでも自由文だけでも回答でき、質問や別案を伝えることもできる。推奨案は表示するが、選択は事前に確定しない。

これはAgentから届いた対応事項への回答の場であり、HumanからAIへの新規相談チャットの入口ではない。Workspace内に一覧を置いても、個々のProject相談・Workspace相談の所有や認可を統合しない。試作の分類・期限・影響・推奨・会話は架空で、実際の相談やAgentの応答には接続しない。

PC 1440px・スマートフォン390pxで一覧・詳細、回答プレビュー、未入力時の案内、0件の空状態、横方向にはみ出さない表示を確認した。コンソールエラーはない。回答の送信・永続化・状態変更・Agent起動は行わず、実際の相談の受入や解決の証拠にはしない。

## Outcome追加のラフ

達成条件は状態・確認方法・任意の目標値を一組とし、現行のOutcome入力契約に合わせて1〜10件を扱う。条件を追加・削除でき、最後の1件は削除できない。独立したSuccess Metrics管理機能を追加する意味ではない。現行の必須項目を表示しているが、フォームの最終的な名称・必須条件・作成後の更新契約は構造化設計と併せて確認する。

## Outcome一覧のラフ

Workspaceの固定メニューは「概要 → 対応待ち → Outcome → Activity → Agent管理 → 設定」の順にする。PCの左メニューとスマートフォンのメニューで順序を揃える。「Outcome」からビジネス目標をまたいだ一覧を開く。PCでは目的、Task進捗、止まっている問題を同じ行の3列で比較し、スマートフォンではOutcomeごとのカード内で縦に表示する。各Outcomeは所属するビジネス目標、名称、目標への貢献仮説、提供状況、効果の確認状況、関連Projectを持つ表示案とする。名称からOutcome詳細、目標名から目標詳細、Project名からProject概要へ進む。

Task進捗は関連するTarget Projectの当該OutcomeのTaskを集約し、受入済み／対象件数と割合を表示する。Project別の進捗と集約範囲を区別し、一覧とOutcome詳細は同じ集計を使う。Task進捗を効果の達成率として扱わず、提供状況と効果の確認状況は別に表示する。試作の第1Outcomeは2 Projectで受入済み12／20件、Projectごとの例は6／10件とする。数値とTargetは架空の例で、正式な重み付け・取消・0件・分母変動の規則やServer集計を決定するものではない。

問題欄は代表の理由と「対応待ち／Agentが対処」、残りがあれば「ほかN件」を表示し、Outcome詳細で両方の問題を確認できる。試作は同じ理由をProject間でまとめ、関連するTaskを辿れる。問題の同一性・集約方法・代表の選定規則は表示案であり、本文一致を製品の識別規則にはしない。「なし」はこの試作内の例であり、実接続で問題情報を取得できない場合は不明と区別する必要がある。

検索、ビジネス目標、問題の有無で絞り込める。該当件数・0件・条件解除を用意し、詳細から戻った際は同じページセッション内の条件を保持する。試作は3 Outcomeの架空データを使う。多数件の取得・ページング、提供状況や評価段階による絞り込み、条件のURL保持は未確定。Outcome追加は引き続きビジネス目標詳細の入口を使う。

PC 1440px・スマートフォン390pxで一覧と詳細への導線、問題あり・ビジネス目標の絞り込み、検索0件、条件解除、詳細からの条件保持、関連ProjectのTask進捗集約を確認した。横方向のはみ出し・コンソールエラーはない。実データの取得・認可・集計や最終UIの受入ではない。情報量と配置を現時点の設計基準として採用し、利用時のフィードバックで見直す。

## Outcome詳細のラフ

Outcome詳細は、課題ごとに根拠・解決策・評価計画／結果をまとめて読む構成を採用する。課題一覧と解決策一覧を別々の主情報へ分割せず、関係を同じまとまりの中で辿れるようにする。施策詳細との役割分担や独立ページの必要範囲は引き続き検討する。

上部はOutcomeの名前、独立した提供状況・効果の確認状況、目標への貢献仮説、受入済みTaskを分子とするTask進捗、進行を妨げる問題と対応への入口を置く。その下に「解決したい課題」を並べ、ユーザーの課題と開発上の障害を区別する。

課題ごとのまとまりは、課題の記述と根拠の状態、観測内容、根拠を確認する入口、解決策と仮説、評価計画、評価結果とする。評価計画は開いて読める仮の操作を用意し、確かめること・方法・判断条件・観測／中止条件を表示する。別のSuccess Metrics管理機能は追加しない。課題に対する複数案や複数評価の最終的な表示方法は未確定。

サンプルには、途中離脱を観測したが理由は未確認の課題と、根拠がまだ不足している課題を含める。途中離脱から原因を断定せず、未実施のウォークスルーや計測を実証済みと表示しない。根拠の文章・イベント件数・進捗・状態は全て架空で、実際の調査・計測・実行管理には接続しない。画面の追加はProblem／Solution等の業務Entityや認可・公開APIの追加を決めるものではない。

## 施策詳細のラフ

目標詳細はいったんたたき台として次へ進むが、後の画面とのつながりを見て再調整できる。施策詳細は、狙うOutcome・仮説、各Projectが提供する機能と開発状態、指標と効果の確認状況、進行を妨げる問題をまとめる。関連Projectは概要へ辿り、そこからStory・Task・PRへ掘り下げる。

目標の数値の変化と、施策が引き起こした効果は区別する。提供前の機能の効果を実証済みとはせず、未接続時は判断不能を示す。全情報は架空データ。対応待ち・問題の操作先は、今回の詳細設計の対象外の簡易表示を含む。

## 実装に向けて残る確認

1. 既存実装と採用した画面を照合し、流用・変更・追加が必要な範囲を特定する。独立した新規実装として重複させない。
2. Human認可のWorkspace統一、Intent・Outcomeの構造化、GitHubのPR・SHA照合、実行状況・公開確認等の契約変更とUI変更を分けてStory・Taskへ落とす。各節の未確定事項はTaskの設計・受入条件で具体化する。
3. 状態別表示、権限不足、読込失敗、保存競合、対象なし、件数増加時の検索・ページングを補完する。未計測・未接続・判断不能を成功やゼロ件に置き換えない。
4. 受入に必要な状態を公開入口・許可済みの検証準備で作れるよう依存順序を整理する。採用したPC／スマートフォンの導線を、実データ・実認可に接続した画面で検証する。
5. 概要から詳細、関連する仕事、コメント・フィードバック、対応待ちへの一連の操作を通して確認する。静的試作の確認を、業務機能の受入や自律運転の実証として扱わない。
